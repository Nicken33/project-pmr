# Регламент работы с Git: ветки, коммиты и Pull Request (PR)

## 1. Базовые термины (Словарь)
- **Ветка (branch)** — изолированная копия кодовой базы для работы над конкретной задачей, которая не ломает стабильный код проекта.
- **PR (Pull Request)** — запрос на слияние изменений из вашей рабочей ветки в основную ветку `main`.
- **Ревью (Code Review)** — этап проверки кода другим участником команды перед слиянием PR[cite: 15].

---

## 2. Работа с ветками
- **Основная ветка `main` защищена:** прямые коммиты и пуши в `main` запрещены(можно только сис.админу(мне)); все изменения вливаются исключительно через Pull Request[cite: 15].
- **Создание отдельной ветки под каждую задачу:** разработка ведётся в ветке, ответвлённой от актуального `main`[cite: 15].
- **Формат именования веток:** `<тип>/<НОМЕР-ТАСКИ>-<краткое-описание>`[cite: 15].
  - Примеры префиксов:
    - `feat/` — новая функциональность (например, `feat/CYB-55-activities-list`)[cite: 15].
    - `fix/` — исправление ошибки (например, `fix/CYB-60-db-connection`).
    - `docs/` — обновление документации (например, `docs/CYB-171-git-rules`)[cite: 15].
    - `Docs/`- обновление документов (Например, git)
---

## 3. Правила оформления коммитов
- **Формат сообщения коммита:** `<НОМЕР-ТАСКИ>: что сделано`[cite: 15].
  - Пример: `CYB-55: добавить список активностей`[cite: 15].
  - Пример: `CYB-171: создать регламент работы с git`[cite: 15].
- **Безопасность данных (Строгий запрет):**
  - **Запрещено коммитить файлы `.env`, приватные SSH-ключи, пароли и токены доступа**[cite: 15].
  - Все переменные окружения должны оставаться локальными; в репозиторий передаётся только публичный шаблон `.env.example`[cite: 4, 15].

---

## 4. Оформление Pull Request (PR)
Каждый PR должен содержать:
1. **Понятное описание:** кратко изложите суть внесённых изменений[cite: 15].
2. **Инструкцию по проверке:** пошагово укажите команды или действия, необходимые для тестирования (например: `docker compose up -d`, открыть страницу, проверить данные)[cite: 4, 15].
3. **Скриншоты / демонстрацию:** если задача затрагивает UI или вёрстку экрана, прикрепление скриншота обязательно[cite: 15].
4. **Ревью и слияние:** перед вливанием в `main` PR должен пройти проверку и получить одобрение тиммейта[cite: 15].
