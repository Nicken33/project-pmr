# Публичный бэкенд для витрины на Vercel

Черновик задачи, а не применённое изменение. Код в этой ветке **не правился**:
документ фиксирует, что именно сломается при публикации витрины на Vercel и какие
правки нужны, чтобы этого не случилось.

## 1. Зачем это нужно

Сейчас API доступен только по VPN-адресу `26.52.103.163:8080`. Serverless-функции
Vercel в VPN не ходят, поэтому витрина с Vercel физически не сможет ни отрисовать
каталог на сервере, ни провести вход через BFF. Нужен публичный HTTPS-origin,
который закрывает `/api/*` и `/media/*`, и решение по IP-адресу посетителя для
лимитера входа.

## 2. Схема после публикации

```text
браузер ──► https://<site> (Vercel)
              ├─ страницы/RSC ──────────────► Next на Vercel
              ├─ POST /api/auth/* ──────────► BFF на Vercel ──► https://<api> ──► api:8080
              ├─ GET /api/v1/* ─────────────► https://<api> (CORS)
              └─ GET /media/* ──────────────► rewrite ──────► https://<api>/media/*

сервер Vercel (SSR) ──► https://<api>/api/v1/*  и  /api/auth/me
```

Требования:

1. `api.<домен>` (или отдельный домен) резолвится в публичный IP; A/AAAA-запись
   есть **до** выпуска сертификата.
2. Наружу открыт 443 (и 80 для ACME/redirect); `8080` и `5432` — нет.
3. Перед `api:8080` стоит reverse proxy с TLS. Он же отдаёт `/media/*` из
   `/srv/media`, потому что Go этот префикс не обслуживает.
4. `ALLOWED_ORIGINS` содержит точный origin витрины.
5. `NEXT_PUBLIC_API_URL=https://<api>` на Vercel; без `/api` на конце.

Минимальный Caddy для API-only (витрину раздаёт Vercel, поэтому `handle` для
`web:3000` не нужен):

```caddyfile
{$API_DOMAIN} {
    handle /api/* {
        reverse_proxy api:8080 {
            header_up X-Real-IP {remote_host}
        }
    }

    handle_path /media/* {
        root * /srv/media
        file_server
    }
}
```

Это вариант `infra/Caddyfile:39-52` без маршрута на витрину. Если оставить полный
стендовый Caddyfile, ничего не сломается: `/` просто будет отдавать локальную
витрину, которую с Vercel никто не запрашивает.

## 3. HTTPS, куки и CORS: почему нельзя «просто открыть порт»

**Браузерный каталог.** Страница Vercel отдаётся по HTTPS. Если
`NEXT_PUBLIC_API_URL` указывает на `http://…`, браузер заблокирует запросы как
mixed content — каталог останется пустым, а в консоли будет ошибка. Это не
зависит от кода приложения.

**Пароль и кука в пути BFF → API.** BFF на Vercel получает пароль посетителя и
пересылает его на API. Без TLS этот пароль и `Set-Cookie` идут по интернету
открытым текстом. Даже если вход «сработает», это утечка учётных данных.

**Атрибут `Secure`.** Бэкенд ставит `Secure` только когда видит
`X-Forwarded-Proto: https` (`backend/Talentro/internal/auth/session.go:139-141`).
BFF пересылает этот заголовок из запроса посетителя
(`web/src/app/api/auth/[...action]/route.ts:50-57`), поэтому при HTTPS-витрине
кука выходит `Secure`. Если завершать TLS негде и заголовок не приходит, кука
уйдёт без `Secure`; браузер её примет, но защита от передачи по HTTP потеряется.

**SameSite и прямой вызов API.** Кука `SameSite=Lax` (`session.go:102-110`)
рассчитана на first-party сценарий через BFF. Если браузер пойдёт за входом
напрямую на `https://<api>`, кука станет third-party: `Lax` не отправит её в
cross-site запросе, а браузеры с блокировкой сторонних кук могут её не сохранить.
Получится «вход прошёл, а `/me` — аноним». Поэтому авторизация только через
BFF, а прямой API-origin нужен для каталога и медиа, не для входа.

**CORS.** `ALLOWED_ORIGINS` — точный список, без wildcard
(`backend/Talentro/internal/delivery/http/cors.go:5-43`). Для production-домена
Vercel:

```dotenv
ALLOWED_ORIGINS=https://<site>
```

Пустое значение не ломает SSR, но браузерные ответы API читать нельзя:
preflight получит 403, а ответ без `Access-Control-Allow-Origin` браузер
отбросит. Каждый preview-домен — отдельная строка; шаблонов нет.

**SSR-hairpin.** Серверные компоненты Vercel ходят в `NEXT_PUBLIC_API_URL`
напрямую, то есть в публичный origin. Он должен отвечать с публичного IP, а не
только изнутри VPN.

## 4. Проблема: за Vercel все посетители — один IP

Это не гипотеза, а следствие текущего кода:

- BFF собирает заголовки для бэкенда и **не передаёт** `X-Forwarded-For`
  (`web/src/app/api/auth/[...action]/route.ts:49-67`).
- Caddy ставит `X-Real-IP {remote_host}` (`infra/Caddyfile:41`), то есть адрес
  TCP-соединения с Caddy. Для запросов из Vercel это egress-IP функции Vercel,
  а не IP посетителя.
- `ClientIP` при приватном пире сначала читает `X-Real-IP`, потом первый адрес
  `X-Forwarded-For` (`backend/Talentro/internal/auth/limiter.go:114-135`). При
  публичном пире (API опубликован напрямую, без прокси) заголовки вообще
  игнорируются и берётся `RemoteAddr` — для Vercel это опять egress-IP.
- Лимиты: вход — 10 попыток в минуту, регистрация — 3 в час
  (`backend/Talentro/internal/delivery/http/handlers/auth_local.go:20-23`).

Итог: все посетители Vercel попадают в один счётчик. Десять неудачных входов
любого человека за минуту дают `429` **всем** на остаток минуты. Три регистрации
за час закрывают регистрацию **всем** на час. Это не только неудобно: один
злоумышленник бесплатно блокирует вход на сайт.

Дополнительно egress-IP Vercel может меняться между инстансами и проектами.
Тогда окна будут то общими, то разными — предсказуемости это не добавляет, но
проблему не решает.

## 5. Варианты

### Вариант A (рекомендуется): BFF передаёт IP посетителя и секрет

Идея: Vercel доверенно сообщает бэкенду IP посетителя, а бэкенд принимает этот
IP только вместе с секретом, которого нет у клиента.

**Новые переменные**

| Где | Имя | Смысл |
| --- | --- | --- |
| Vercel (server-only) | `AUTH_PROXY_SECRET` | случайные 32 байта, **не** `NEXT_PUBLIC_*` |
| бэкенд | `TRUSTED_PROXY_SECRET` | то же значение |

Оба значения генерируются одинаково: `openssl rand -hex 32`. В клиентский бандл
`AUTH_PROXY_SECRET` не попадает, потому что у переменной нет префикса
`NEXT_PUBLIC_`.

**Правки в web (BFF)**

Файл `web/src/app/api/auth/[...action]/route.ts`, блок `relay` (строки 49-67):

1. Взять IP посетителя из `x-forwarded-for` (первый валидный адрес) или
   `x-real-ip`; проверить через `node:net` `isIP`, чтобы в заголовок не уехала
   произвольная строка.
2. Если `process.env.AUTH_PROXY_SECRET` задан и IP валиден — добавить к
   upstream-заголовкам:
   - `x-forwarded-for: <IP посетителя>`;
   - `x-talentro-proxy-secret: <AUTH_PROXY_SECRET>`.
3. Сохранить существующую пересылку `cookie` и `x-forwarded-proto`.
4. Если секрет не задан — оставить поведение как сейчас (общий счётчик), но
   записать предупреждение в лог старта/запроса, чтобы режим не был «тихим».

Важно: Vercel сам проставляет `x-forwarded-for` на входе в функцию; проверьте на
своём деплое, что там именно IP посетителя, а не цепочка из чужих прокси. Первый
валидный адрес — то, что нужно. Не доверяйте заголовку, если запрос пришёл не
через Vercel (например, прямой вызов BFF по IP) — в этом случае лучше не
передавать IP вовсе.

**Правки в backend**

1. `backend/Talentro/internal/config/config.go`: добавить поле
   `TrustedProxySecret` и чтение `os.Getenv("TRUSTED_PROXY_SECRET")`.
2. `backend/Talentro/internal/auth/limiter.go`: изменить сигнатуру
   `ClientIP(r *http.Request)` → `ClientIP(r *http.Request, trustedSecret string)`.
   Порядок:
   - если `trustedSecret != ""` и `X-Talentro-Proxy-Secret` совпал
     (constant-time, как `subtle.ConstantTimeCompare` в `handlers/auth.go`),
     взять первый валидный адрес из `X-Forwarded-For` и вернуть его;
   - иначе — текущая логика (`X-Real-IP` при приватном пире, затем `XFF`,
     затем `RemoteAddr`).
3. `backend/Talentro/internal/delivery/http/handlers/auth.go`: сохранить секрет
   в `AuthHandler` из `cfg` и передавать его в `ClientIP`.
4. `backend/Talentro/internal/delivery/http/handlers/auth_local.go:49,116`:
   обновить вызовы `auth.ClientIP(r, h.trustedProxySecret)`.
5. `backend/Talentro/internal/auth/limiter_test.go`: добавить таблицы
   «секрет верный / неверный / пустой», «XFF подделан без секрета»,
   «несколько адресов в XFF — берём первый», «IP с портом отбрасывается».
6. `docker-compose.yml`, `.env.example`, `docs/deploy.md` §3: добавить имя
   `TRUSTED_PROXY_SECRET` (значение пустое в примере, комментарий о том, что
   пусто = старое поведение).

**Caddy**

Функционально менять ничего не нужно: Caddy по умолчанию пропускает
`X-Talentro-Proxy-Secret` наверх и **дописывает** свой адрес в
`X-Forwarded-For`; первый адрес остаётся адресом посетителя, который передал
BFF. `X-Real-IP` Caddy продолжает ставить из `{remote_host}`, но бэкенд при
валидном секрете смотрит на `X-Forwarded-For` раньше.

Проверьте access-log Caddy: если он пишет заголовки запроса, секрет попадёт в
лог. Настройте редактирование этого поля или не логируйте заголовки. Секрет в
логах — это утечка доверия.

**Свойства**

- Запрос без секрета не может подделать IP: `X-Forwarded-For` игнорируется,
  `X-Real-IP` Caddy ставит из реального TCP-пира.
- Запрос с секретом доверенный: его может прислать только BFF (или тот, кто
  украл секрет — поэтому секрет хранится только в env и не логируется).
- Секрет не в клиентском бандле: проверяется grep по чанкам (п. 6).
- Если `AUTH_PROXY_SECRET`/`TRUSTED_PROXY_SECRET` не заданы, поведение
  откатывается к текущему — общий счётчик. Это осознанный fallback, а не
  «безопасно по умолчанию».

**Проверка после внедрения**

1. Два разных внешних IP (например, офис и телефон в мобильной сети): по 10
   неверных входов с каждого. На 11-й попытке `429` должен получить только тот
   адрес, который исчерпал свой лимит; второй продолжает получать `401`.
2. Тот же тест на регистрацию: 3 с одного IP, четвёртая — `429`; с другого IP
   регистрация проходит.
3. Подделка без секрета:
   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://<api>/api/auth/login \
     -H 'content-type: application/json' \
     -H 'X-Forwarded-For: 203.0.113.7' \
     -d '{"email":"nobody@example.com","password":"wrong"}'
   ```
   Повторить 11 раз: должна включиться блокировка по реальному адресу
   отправителя, а не по `203.0.113.7`.
4. В бандле витрины нет значения `AUTH_PROXY_SECRET` и `TRUSTED_PROXY_SECRET`.

**Цена**

- Две новые переменные и синхронная ротация: сменили на Vercel — сразу смените
  на бэкенде, иначе IP перестанет передаваться (вернётся общий счётчик, вход не
  сломается).
- Одна точка доверия: если секрет утечёт, атакующий сможет подставлять любые IP.
  Поэтому секрет не в git, не в логах, не в клиентских сборках.
- Это всё ещё in-memory лимитер: при нескольких экземплярах API счётчики не
  общие. Для одного VDS этого достаточно; при горизонтальном масштабировании
  понадобится общее хранилище (Redis/Postgres), но это отдельная задача.

### Вариант B: не менять код, поднять лимиты

Можно оставить общий счётчик и увеличить `loginAttempts`/`registerAttempts`
(`auth_local.go:20-23`) до, например, 1000/100. Минус: лимит перестаёт защищать
от перебора паролей, а один злоумышленник всё равно может выжечь общий счётчик —
просто позже. Для публичного сайта это не решение.

Можно дополнительно ключевать лимит по `email + IP`: это уменьшит взаимную
блокировку разных пользователей при входе, но регистрация останется общей, и
подбор пароля к одному адресу всё равно нужно ограничивать. Это тоже правка кода,
а не «оставить как есть».

Вариант B допустим только для закрытого демо без публичной регистрации, и даже
тогда его нужно явно записать в риски.

### Вариант B′ (дополнение, не замена): лимит на edge Vercel

Vercel Firewall умеет ограничивать частоту запросов к `/api/auth/*` по IP
посетителя на своей стороне. Это не исправляет счётчики бэкенда, но не даёт
злоумышленнику наполнить общее окно. Доступность функции зависит от плана
Vercel; в рамках этой проверки она не подтверждена. Как единственная мера не
подходит: если edge пропустит запрос, бэкенд снова увидит один IP.

## 6. Чек-лист публикации бэкенда

1. DNS: `api.<домен>` → публичный IP; проверка `dig +short api.<домен>`.
2. Firewall: 443 и 80 открыты, `8080`/`5432` — только приватно.
3. Reverse proxy с TLS поднят; `/api/*` и `/media/*` отвечают.
4. `ALLOWED_ORIGINS` содержит точный `https://<site>`.
5. `NEXT_PUBLIC_API_URL=https://<api>` задан на Vercel **до** сборки.
6. `AUTH_PROXY_SECRET` (Vercel) и `TRUSTED_PROXY_SECRET` (бэкенд) заданы одним
   значением — если выбран вариант A.
7. Снаружи проверены: каталог, CORS, медиа, вход через BFF, атрибуты куки
   (команды — `docs/vercel.md` §8).
8. Два разных внешних IP дают независимые лимиты (вариант A).
9. В логах нет паролей, кук и секрета; access-log Caddy проверен.
10. Бэкап базы снимается и уезжает за пределы сервера.

## 7. Чего нет у владельца

Полный список — `docs/vercel.md` §9. Для этой задачи критичны: публичный
домен/IP для API, DNS-доступ, SSH на сервер, право открыть 443 и поставить
reverse proxy, TLS/ACME, а также решение «вариант A или B». Без них документ
остаётся проектом: значений домена, IP и SSH в репозитории нет.
