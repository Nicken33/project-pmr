# Аудит наполнения каталога Talentro — дефициты против ТЗ §11.2

Дата прогона: 05.11.2026 (данные стенда меняются; на следующий день цифры перепроверять).
Источники: живой API `http://26.52.103.163:8080` (только GET), `database/init.sql` и
`database/checks.sql` ветки `.worktrees/integration`, ТЗ v2 (§3.2–3.4, §11),
`docs/acceptance/stand-gaps-2026-11-04.md`, `docs/content/photo-inventory.md`.

Правило: ниже только то, что реально отдаёт API/БД или написано в ТЗ. Ни одного
придуманного названия, телефона, цены или фото.

## 0. Главный контекст, который меняет всё

Вся текущая выдача каталога — **демонстрационный сид**, а не подтверждённые данные:

> `init.sql:11-13`: «Данные ниже — демонстрационные для стенда и тестов: телефоны,
> адреса, координаты и ссылки правдоподобные, но не подтверждённые».

Основание публикации (§11.8) у 8 из 10 организаций — заглушки `https://example.test/…`
(`init.sql:446-480`); реальные формулировки согласия есть только у org 7 и org 9
(«Согласие мастера … получено лично»). `contacts_verified_at` пуст у **всех**
организаций и точек (API: `"contacts_verified_at": null` в каждом ответе
`/api/v1/organizations/*` и в блоках `locations`). То есть даже «что есть» сегодня
нельзя показать пальцем (§11.3). Это отдельный, самый дорогой дефицит: владельцу
нужно не только доносить объём, но и **подтвердить/заменить** демо-строки.

## 3. Честная оценка: что нужно для releasable и что можно выпустить сейчас

### Вариант А — «витрина выглядит наполненной» (минимум, числа округлены вверх)

Ориентиры: пагинация 20 (§3.1.7), доли §11.2, непустые направления (checks №11).

|---|---|---|---|

| Из них услуг (≥20 %) | 4 | 1 | **+3** |

### Вариант Б — ничего не принесли: что можно официально выпустить

С текущим объёмом (8 карточек, 0 фото-файлов, демо-основания) **полноценный релиз
нельзя назвать честным**: нарушение §11.2 (фото 0 % вместо ≥80 %, услуги 12,5 % вместо
20 %) и §11.3/§11.8 (нет ни одного подтверждения источника). Официально выпускаемый
формат — **закрытый стенд / «каталог в наполнении»**:

- явная плашка на каталоге «Каталог наполняется: сейчас N занятий, фото и подтверждённые
  контакты добавляются» (N брать из API-`total`, не хардкодить);
- `about.md` уже написан в этом духе («Чего пока нет»: фото 0, отзывов нет, аккаунтов нет) —
  он годится как публичная декларация;
- обязательное условие даже для этого режима: заглушка «Фото нет» остаётся легальной
  только для <20 % карточек (§11.2), поэтому 7 файлов обложки — минимальный взнос даже
  для «беты»;
- демо-телефоны `+373 777 …` до публичного показа должны быть либо подтверждены, либо
  закрыты дисклеймером «стенд» — инициатива `init.sql:11-13` это прямо констатирует.

## 4. «Расписание уточняется» на всех 8 карточках — вывод: КОД (контракт/маппинг), данные есть

Доказательная цепочка:

1. Данные в API есть: `GET /api/v1/activities/{slug}` для **всех 8** слагов возвращает
   непустой `groups[].schedules` — прогон сегодня: 23 строки расписания на 14 опубликованных
   групп, минимально 1 строка на группу (см. `act_*.json`, напр.
   `tiraspol-futbol-detyam`: 5 строк). Сид: `init.sql:563-589` (25 строк `schedules`).
2. Список витрины строится из **плоского** `GET /api/v1/activities`, у строк которого
   полей `groups`/`schedules` нет в контракте вообще (`api.ts:45-85` interface `ApiActivity`
   — только `group_id/group_name/age/price/seats`; подтверждено ответом API сегодня).
3. Маппер списка жёстко ставит пустое расписание:
   `web/src/lib/api-server.ts:136-153` — `groupFromListItem()` возвращает группу с
   `schedule: []` (строка 150). Это сознательное «не выдумываем» (комментарий
   `api-server.ts:38-43`), но для §3.2 («расписание раскрытой группы одной строкой» —
   обязательный элемент карточки в списке) итог = дефект.
4. `ActivityCard.tsx:259-262`: `formatSchedule(group) || "Расписание уточняется"`;
   `filters.ts:541-542` при `schedule.length === 0` возвращает `""` → надпись на каждой карточке.
5. Страница каталога идёт именно этим путём: `app/page.tsx:77` → `fetchCatalogFromApi`.

Вывод: **это не дефицит наполнения, а дефект кода/контракта** — починка на стороне
бэкенда (добавить сводку расписания подобранной группы в строку списка, таблица
`schedules` уже связана с `group_id`) или фронтенда (подтягивать детали). От владельца
для этой задачи не нужно ничего; приоритет — инженерная P1, а не контентная.

## 5. Возраст репетитора (id 9) — вывод: ДАННЫЕ (пусто в БД), и это норма ТЗ, а не дефект
