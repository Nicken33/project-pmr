# Чистая витрина на данных БД + аккаунт тестировщика

Дата: 2026-11-04
Ветка: `feat/15-clean-site-tester-session` (base — `feature/frontend-audit-tz-sync`, после мержа PR #2 переставляется на `main`)
Задачи: №15 (чистая витрина на реальных данных), №16 (серверная сессия и аккаунт тестировщика)

## 1. Постановка

Сайту сейчас нельзя показать постороннему: витрина собрана из 97 КБ моков в
`web/src/lib/data.ts`, а Go-бэкенд отдаёт только `GET /health` и `GET /api/cards`
с шестью полями из двенадцати. Обычный посетитель видит «Выбор редакции»,
чипы «часто ищут», счётчики «10 вариантов», фейковый колокольчик с двумя
уведомлениями, фейковые телефон и почту в футере и статистику на «О проекте» —
всё это нарисовано вместе с интерфейсом и не является данными продукта.

Решения, зафиксированные с владельцем:

1. Граница чистоты — **только данные из БД**. Всё, у чего нет серверного
   источника, обычному посетителю не показывается.
2. Механика «видеть всё» — **серверная сессия в HttpOnly-куке**, а не флаг в
   localStorage.
3. Бэкенд **доделывается**, чтобы чистая версия была рабочей, а не пустой:
   координаты, страница занятия, организации, справочник категорий.

## 2. Не цели

- Не делаем настоящую модерацию, приём анкет и отзывы на сервере: эти разделы
  остаются моковыми и доступны только тестировщику.
- Не делаем таблицу `sessions`, выход по токену отзыва и ротацию секретов — для
  стенда достаточно подписанной куки со сроком.
- Не трогаем дизайн-систему, кегль и тап-зоны: они приведены к ТЗ в задачах №9 и
  №11 и менять их здесь незачем.
- Не переписываем легаси-`src/` в корне репозитория: он не входит в сборку `web/`.

## 3. Модель данных (`database/init.sql`)

Все изменения идемпотентны (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT
EXISTS`, `ON CONFLICT DO NOTHING`, `setval`), скрипт можно запускать поверх
живого стенда повторно.

```
organizations(id SERIAL PK, slug VARCHAR(80) UNIQUE, name VARCHAR(200),
              city_id INT REFERENCES cities(id), description TEXT,
              phone VARCHAR(50), email VARCHAR(120), address TEXT, link VARCHAR(500))

card_locations(id BIGSERIAL PK, card_id BIGINT REFERENCES cards(id) ON DELETE CASCADE,
               name VARCHAR(200), address TEXT, district VARCHAR(100),
               lat NUMERIC(9,6), lng NUMERIC(9,6))
  + индекс card_locations_card_id_idx

categories(id SERIAL PK, name VARCHAR(100) UNIQUE, parent_id INT REFERENCES categories(id))
cards.direction_id INT REFERENCES categories(id)   -- добавить колонку, заполнять сидом

users: добавить email VARCHAR(160) UNIQUE, name VARCHAR(120), avatar_url VARCHAR(500),
       provider VARCHAR(20) DEFAULT 'local', google_sub VARCHAR(64),
       role VARCHAR(20) DEFAULT 'user'
```

Сид: 8 организаций под текущие `cards.organization_id` (1–8), по одной–две точки
на анкету с настоящими координатами городов (Тирасполь 46.8416/29.6447, Бендеры
46.8328/29.2556, Рыбница 47.7667/29.5836, Дубоссары 46.8614/29.6206, Каменка
48.0398/29.3074, Слободзея 46.7100/29.7670) — все внутри рамки Приднестровья
45.9–48.9 / 27.4–30.6, которую проверяет `validateCoordinates()`. Справочник
категорий — из §4.5 ТЗ (9 направлений верхнего уровня + категории), `direction_id`
анкетам соответствует их текущая `category`.

Анкет в сиде остаётся 8, из них 6 `published`. Это по-прежнему тестовые данные, и
в UI они не подаются как проверенные: ни бейджа «данные подтверждены», ни
счётчиков, ни «выбора редакции» на их основе.

## 4. Контракт Go

- `GET /api/cards` — полный `SELECT` по `models.Card` (сейчас в запросе 5 колонок
  из 12, поэтому `price`, `category`, `district`, `description`, `link` всегда
  `null`) плюс `org_id`, `slug` организации. Фильтры `direction`, `price_max`,
  `q` раскомментируются и реализуются; `q` ищет по `name ILIKE` и `description ILIKE`.
- `GET /api/cards/{id}` — карточка целиком + `locations[]` + вложенная
  `organization`. 404 для несуществующего и для не-`published`.
- `GET /api/categories` — справочник (нужен фронту, чтобы не держать 49 категорий
  в моках).
- `POST /api/auth/tester` — `{ "token": "..." }`, сверка с `TESTER_TOKEN`, выдаёт куку.
- `POST /api/auth/google` — существующая верификация ID-токена + проверка `aud`
  становятся обязательными (без `GOOGLE_CLIENT_ID` — 503, а не «пропускаем»), затем
  upsert пользователя по `google_sub` и выдача куки.
- `GET /api/auth/me` — по куке отдаёт `{ authenticated, tester, role, name, email }`;
  без валидной куки — 200 с `authenticated: false` (это не ошибка, а состояние).
- `POST /api/auth/logout` — снимает куку.
- CORS остаётся списком `ALLOWED_ORIGINS`; с куками `Allow-Credentials: true`
  требует точного `Origin`, звёздочка недопустима.

Новые переменные: `SESSION_SECRET` (HMAC-ключ), `TESTER_TOKEN`. В `.env.example` —
только плейсхолдеры, значений секретов в репозитории нет и не будет (§3 регламента).

## 5. Сессия

Подписанный payload `base64(json).hmac_sha256(secret || payload)`, кука
`talentro_session`, `HttpOnly`, `SameSite=Lax`, `Secure` если заголовок
`X-Forwarded-Proto=https` или проставлен флаг, `Max-Age` 30 дней, путь `/`.
Проверка — `hmac.Equal` по постоянному времени. Просроченный `exp`, битая
подпись или неизвестный вариант — считаем неаутентифицированным, 401 на
защищённых вызовах и `authenticated: false` на `/me`.

Тестировщик — это роль в payload, а не отдельная таблица: `tester: true` даёт
доступ к мок-витрине, `/moderation` и `/account`. Обычный Google-пользователь
получает `role: "user"` без тестовых разделов.

## 6. Граница «чистого» — на сервере

Механика, а не косметика: серверный компонент читает куку (`cookies()` из
`next/headers`, в Next 16 — асинхронный вызов), зовёт `GET /api/auth/me` с
пересылом куки и **до** загрузки данных решает, какие коллекции поднимать. Если
мок просто не отрисовать, он всё равно сериализуется в RSC-поток — ровно та
утечка, которую я закрывал на `/moderation` в PR #2.

Фронтовая граница — чистая функция `resolveViewMode(session): "real" | "demo"` в
`web/src/lib/view-mode.ts`, единственное место, где известно, что такое «тестер».

Обычному посетителю:

| Раздел | Поведение |
|---|---|
| Каталог, фильтры | только `/api/cards`; без `NEXT_PUBLIC_API_URL` или при недоступном бэкенде — панель «Каталог не загрузился / Повторить», фолбэка на моки нет |
| `/map` | маркеры из `card_locations`; пустой результат объясняется текстом, а не моками |
| `/activities/[slug]` | `GET /api/cards/{id}`; блока отзывов, «похожих» и голосов нет |
| `/organizations/[slug]` | организация из БД + её анкеты; связывающих таблиц с отзывами нет |
| `/favorites` | пустое состояние, пресеты возраста и моковые карточки не подгружаются |
| «Выбор редакции», «часто ищут», счётчики, уведомления в шапке, контакты в подвале, статистика «О проекте», баннер «черновик» | не рендерятся и не передаются клиентом |
| `/account`, `/moderation` | 404-экран «Раздел доступен по тестовому входу» без каких-либо коллекций в ответе |

Тестировщику с валидной кукой — всё перечисленное возвращается без изменений
поведения, включая моки и кабинеты.

`AppProviders` перестаёт выводить роль из подстроки e-mail (`moder`/`owner`):
источник — `/api/auth/me`. `loginWithGoogle` вызывает `POST /api/auth/google` и
берёт профиль с сервера; клиентское `jwtDecode` остаётся только для мгновенной
отрисовки аватара до ответа, права доступа из него не выводятся. `demoUser`
«Анна Морозова» из `AppProviders` убирается: аноним не получает фиктивную
личность, состояние «не входит» отличается от состояния «вошёл».

На `/login` кнопка Google остаётся видимой всем (это настоящий вход, а не
пример), рядом — отдельная форма «Вход для проверки» с полем токена; она не
притворяется основным способом аутентификации и не показывает подсказок с самим
токеном. Слаг организации в сиде — латиница (`studiya-palitra`), по нему и
ищется `/organizations/[slug]`.

## 7. Тесты и приёмка

Go: табличные тесты на подпись/проверку куки (битая подпись, просроченный `exp`,
чужой секрет), на сверку `TESTER_TOKEN`, на обязательность `aud` при верификации
Google (верификатор выносится в интерфейс, сеть не дёргается), на форму ответа
`/api/cards/{id}` и на список CORS.

Vitest: `resolveViewMode` (нет сессии / тестер / обычный пользователь / 500 от
`/me`), честность маппинга новых полей `locations → coordinates`, отсутствие в
маппинге выдуманных значений там, где сервер отдал `null`.

Приёмка живым стендом (Postgres 55432 + Go 8080 + прод-сборка):

1. `psql -f database/init.sql` поверх живой БД — без ошибок, повтор запускаем
   дважды.
2. `curl /api/cards` — 6 анкет, у каждой заполнены `price`, `category`,
   `district`, `org_id`.
3. `curl /api/cards/1` — карточка с `locations[]` и `organization`.
4. `curl /api/cards/7` и `/api/cards/999` — 404 (не `published` / нет строки).
5. Анонимный `curl http://localhost:3009/` и `/map`, `/favorites`,
   `/organizations/studiya-palitra`: греп `Палитра|Киберход|часто ищут|Выбор
   редакции|+373 777` — **0 совпадений** (кроме тех, что реально лежат в БД).
6. Тот же запрос с кукой тестера — моки присутствуют.
7. `/map` в браузере: маркеры соответствуют числу строк в `card_locations` для
   `published`-анкет, видимая область не сбрасывается при смене фильтра.
8. Статические гейты: `go vet`, `go test`, `tsc --noEmit`, `vitest run`,
   `eslint src`, `next build` — без ошибок.

## 8. Риски

- **Пустой сайт без бэкенда.** После отказа от мокового фолбэка прод-витрина без
  `NEXT_PUBLIC_API_URL` показывает состояние ошибки. Это намеренно: тихая подмена
  моками и есть то, от чего чистим.
- **Публичный токен тестировщика.** Он в env и не секретируется UI; доступ к
  мокам — не привилегия, а витрина. Настоящих персональных данных в моках нет.
- **Пересылка куки из RSC в Go.** Нужен `credentials`/проброс заголовка `Cookie`;
  если бэкенд за тем же доменом — CORS не потребуется, но на стенде порты разные,
  поэтому `ALLOWED_ORIGINS` обязателен.
- **Объём.** Правки задевают 8+ серверных страниц и слой данных; PR #2 (197
  файлов) остаётся отдельным, этот — вторым в стопке, base меняется после мержа.
