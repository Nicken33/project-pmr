# CI Talentro: что проверяет пайплайн и чему в нём можно верить

Документ описывает `.github/workflows/ci.yml` (workflow `CI` в
`https://github.com/Nicken33/project-pmr`) — зачем там каждый гейт, что он
ловит, где он умеет врать, и что осталось недоказанным. Задача 20.

Это **единственный** workflow в репозитории. Отдельных `web.yml` / `api.yml` нет
нарочно: два файла плодили бы расхождение в версиях Node/Go и в кэшах, а
разделение уже сделано внутри одного файла на уровне job'ов (их четыре плюс
пробный).

---

## 1. Когда запускается

- `push` в `main` и в рабочие ветки по регламенту `docs/git-rules.md`
  (`feat/**`, `fix/**`, `chore/**`, `docs/**`, `codex/**`);
- любой `pull_request`;
- `workflow_dispatch` — ручной прогон.

`concurrency: ci-${{ github.ref }}` с `cancel-in-progress: true`: пуш в ту же
ветку отменяет предыдущий незавершённый запуск этой же ветки. `permissions:
contents: read` — пайплайн только читает репозиторий, `GITHUB_TOKEN` ему больше
и не нужен.

Ключ триггера в файле записан как `'on':` (в кавычках). GitHub трактует
безкавычное `on` правильно, но YAML 1.1 читает его как булево `true`, и любой
посторонний парсер (включая наш самописный валидатор, §11) спотыкается об это.
Кавычки стоят ничего, а вопрос снимают.

**Важно про `push`:** GitHub берёт файл workflow из пушащегося коммита. Поэтому
на `main` сейчас исполняется редакция `5c753aa` (слияние было до моих правок), а
исправленная версия живёт пока только в `feat/20-ci`. Следствие: `main` краснеет
по устаревшим правилам (§12), и это не баг пайплайна, а следствие того, что
правка ещё не смержена.

## 2. Джобы и что проверяет каждый гейт

| Job | Гейт | Что ловит | Падает ли job |
| --- | ---- | --------- | ------------- |
| `backend` | `gofmt -l .` | расформатированный Go-код | да |
| `backend` | `go build ./...` | код не собирается | да |
| `backend` | `go vet ./...` | подозрительные конструкции (утечки `Context`, `%d` для строки и т. п.) | да |
| `backend` | `go test -count=1 ./...` без `DATABASE_URL` | юнит-логика: auth, cors, route, query, словари | да |
| `backend` | проверка, что `DATABASE_URL` пуст | герметичность: job не должен тайком зависеть от базы | да |
| `backend-integration` | `psql -v ON_ERROR_STOP=1 -f database/init.sql` | схема и сиды применяются без ошибок | да |
| `backend-integration` | `count(*) FROM cards WHERE status = 'published' >= 1` | сиды не опустели | да |
| `backend-integration` | `go test -v ./internal/repository/...` с `DATABASE_URL` | семантика фильтров §5 против настоящего Postgres | да |
| `backend-integration` | анти-ложно-зелёный guard (§5.4) | тесты скипнулись, а job выглядит зелёным | да |
| `web` | `npm ci` | `package-lock.json` расходится с `package.json` | да |
| `web` | `npm run lint -- --max-warnings=14` | ошибки eslint и рост числа предупреждений | да |
| `web` | `tsc --noEmit` | типы | да |
| `web` | `npm test` (vitest) | юнит-тесты витрины | да |
| `web` | `npm run build` (next build) | сборка и генерация маршрутов | да |
| `web` | `git check-ignore web/.next web/node_modules` | артефакты сборки не попадут в коммит | да |
| `mobile-detect` | есть ли `frontend/mobile/pubspec.yaml` | — (пишет output) | нет |
| `mobile` | `flutter analyze`, `flutter test` | мобильный клиент | да, но только если проект в ветке |

Про `-count=1`: Go переиспользует результаты тестов из build-кэша, а `setup-go`
этот кэш восстанавливает. Без `-count=1` незатронутый пакет мог бы «пройти»,
используя результат прошлого прогона.

Про `--max-warnings=14`: в `web/` сейчас 14 предупреждений и 0 ошибок (проверено
локально). Без порога job вечно зелёный, потому что предупреждения не валят
eslint; с нулём — сразу красный из-за чужого долга. 14 — это «текущий уровень не
растёт», обычный ratchet. Когда долг разгребут, число нужно уменьшить, а не
увеличивать.

## 3. Версии инструментов и кэш

- **Go** берётся из `backend/Talentro/go.mod` (`go 1.27.2`) через
  `go-version-file`, а не прописан числом, чтобы раннер и разработчик не
  разъезжались.
- **`cache-dependency-path: backend/Talentro/go.sum` обязателен.** В первой
  редакции кэш не восстанавливался, и прогон `42057987868` (это `main`) принёс
  ровно эту строку в аннотации: `Restore cache failed: Dependencies file is not
  found in /home/runner/work/project-pmr/project-pmr. Supported file pattern:
  go.sum`. Action искал `go.sum` в корне репозитория.
- **Node 24, без матрицы 22.x/24.x.** Единственные заявленные ориентиры —
  `web/Dockerfile` (`ARG NODE_VERSION=24`) и `docs/deploy.md`; в
  `web/package.json` секции `engines` нет, `.nvmrc` в репозитории тоже. Матрица
  удвоила бы время и расход раннеров ради версии, которую никто не запускает и
  не разворачивает. Если 22.x всё-таки нужен как поддержка — скажите, это
  две строки `strategy.matrix`, но тогда и в Dockerfile должна появиться
  соответствующая ветка.
- **Кэш npm** — встроенный в `setup-node` (`cache: npm`,
  `cache-dependency-path: web/package-lock.json`), кэш Go — встроенный в
  `setup-go`. Отдельные `actions/cache` не подключали, чтобы не держать два
  источника ключей.
- **Версии actions — `checkout@v7`, `setup-go@v7`, `setup-node@v7`.** Причина
  конкретная: прогон `42057987868` выдал `Node.js 20 is deprecated. The
  following actions target Node.js 20 but are being forced to run on Node.js
  24: actions/checkout@v4, actions/setup-go@v5`. После перехода на v7
  предупреждений по версиям actions нет (прогон `42088228822`, аннотации —
  только служебное сообщение про образ раннера).
- `backend/go.mod` — отдельный legacy-модуль `cli-city-filter`. Он **не**
  гейтится намеренно: это не продукт, и его формат/тесты не должны блокировать
  мерж витрины. Если решите его чинить или удалять — скажите, тогда добавим шаг.

## 4. Мобильная ветка: почему `detect` + `skipped`

Flutter-код живёт в чужом worktree (`mobile`) и в `feat/20-ci` его нет. Если бы
job `mobile` запускался безусловно, каждая ветка была бы красной с
`flutter: command not found` — то есть гейт сразу терял смысл. Поэтому маленький
`mobile-detect` пишет в output `enabled=true/false`, а `mobile` идёт под
`if: needs.mobile-detect.outputs.enabled == 'true'`.

Стоит ~10 секунд, зато как только `frontend/mobile/pubspec.yaml` появится в
ветке, `flutter analyze` и `flutter test` включатся сами, без правки workflow.

**Честно:** шаги `mobile` ни разу не исполнялись (в прогонах job всегда
`skipped`). Синтаксис `flutter-action@v2` проверен только парсером YAML.

## 5. Postgres и интеграционные тесты

### 5.1 Какие тесты вообще требуют базу

Только `backend/Talentro/internal/repository/catalog_test.go`: `newRepo()`
читает `DATABASE_URL`, при пустом делает `t.Skip(...)`, иначе `db.Ping()`.
Остальной репозиторий герметичен (`dictionaries_test.go` — чистые юниты про
построение дерева категорий). Отсюда два job'а, а не один: без базы
интеграционный прогон бессмысленен, а в общем job'е он бы только затирал
настоящие падения.

Ожидания тестов завязаны на сиды `database/init.sql` — об этом прямо сказано в
шапке файла. Меняете сид — правьте ожидания.

### 5.2 Сервис

`postgres:16` — тот же мажор, что в `docker-compose.yml`, чтобы планировщик и
синтаксис не расходились со стендом. `TZ: Europe/Chisinau` — как в compose
(`TZ: ${TZ:-Europe/Chisinau}`): §7.11 считает «сегодня» по `current_date` базы,
и в UTC тесты расписания живут в другом дне. Health-check — `pg_isready`,
12 попыток по 5 секунд.

### 5.3 Схема, сиды и два гейта до тестов

`psql -v ON_ERROR_STOP=1` — чтобы битый `init.sql` не превратился в невнятное
«тесты упали на пустой базе». `init.sql` требует `pg_trgm` (§5.1, trigram-индекс
для `LIKE '%…%'`) и сам падает без него; список расширений печатается, чтобы по
логу было видно, на чём встало. Второй гейт — проверка, что в базе есть опубликованные
карточки: сиды молча пустеют не первый раз, и тогда все тесты фильтров дают
«получили [], ожидали [...]», а виноватым выглядит фильтр.

Раньше здесь была «мягкая деградация» (не поднялась база — warning и skip). От
неё отказались: молчаливый skip хуже честного красного.

### 5.4 Первый красный был багом CI, а не кода

Прогон `42086657228` (`feat/20-ci`, коммит `15ee5c3`): `backend` зелёный, `web`
зелёный, а `backend-integration` красный на шаге тестов, и вся диагностика
ограничилась аннотацией `FAIL ./internal/repository/... [setup failed]`.

Причина: у job'а не было `defaults.run.working-directory` (он нужен шагам `psql`
с `database/init.sql` из корня), и `go test ./internal/repository/...`
запускался из корня репозитория, где `go.mod` лежит не там:

```
pattern ./internal/repository/...: directory prefix internal/repository
does not contain main module or its selected dependencies
FAIL    ./internal/repository/... [setup failed]
```

Тесты **не выполнились ни разу**. По виду это было как провал сидах, и я
успел выдвинуть гипотезу про коллацию и таймзону (локально те же тесты были
зелёные на PostgreSQL 18 с `--locale=C`). Прогон `42088228822` (коммит
`23c71e8`) гипотезу опроверг: `postgres:16` с коллацией по умолчанию, все
job'ы зелёные. Диагноз «окружение» стоил бы ещё несколько прогонов; диагноз
«каталог» воспроизводится одной командой из корня репозитория.

Что изменено после этого:

1. шаг `Интеграционные тесты репозитория` получает `working-directory:
   backend/Talentro` сам, а job остаётся в корне для `psql`;
2. аннотации забирают не только `--- FAIL` и `_test.go:строка:`, но и строки
   загрузки пакета (`# `, `pattern `, `go: `) — иначе `[setup failed]` снова
   останется единственной подсказкой;
3. **guard против ложного зелёного**: если `rc = 0`, но в логе упоминается
   `DATABASE_URL` (это текст skip-причины) или нет ни одной строки
   `--- PASS: Test`, job падает с внятной ошибкой. Без него шаг без `env` дал бы
   `ok ... 0.65s` (часть тестов — юниты, они проходят всегда), и «интеграционный»
   job проверял бы ровно то же, что герметичный `backend`, оставаясь зелёным.
   Проверял логику на двух синтетических логах: skip-only → guard срабатывает,
   pass → молчит.

### 5.5 Что печатает «Сводка по конфигурации базы»

`server_version`, `datcollate`/`datctype`, `TimeZone`, `current_date`. Дешёвые
четыре строки лога: когда тесты фильтров покраснеют, по ним сразу видно,
разошлось окружение со стендом или это настоящая регрессия. Коллация влияет на
`ORDER BY` строк, `TimeZone` — на `current_date`.

## 6. Windows-ловушки, из-за которых локальный прогон врёт

- **`gofmt -l .` на Windows помечает ВСЕ `.go`-файлы.** `core.autocrlf=true`
  даёт CRLF в рабочем дереве, gofmt считает `\r` частью строки. В индексе лежит
  LF (`git ls-files --eol` → `i/lf w/crlf`), checkout на Linux-раннере отдаёт
  LF, поэтому гейт там честный. Отличить артефакт от настоящего долга:
  `gofmt -l . | tr -d '\r'` — реальные offenders остаются в списке, CRLF-шум
  исчезает. Так я нашёл единственный настоящий пропуск в каноне `3dd0172` —
  `backend/Talentro/internal/delivery/http/handlers/moderation.go`.
- **Лечения локально нет и не будет из моего дерева**: правильный фикс —
  `.gitattributes` с `*.go text eol=lf` (и для `*.yml`, `*.sql`) в корне. Это
  чужие файлы и это решение координатора, я лишь фиксирую как долг: пока его
  нет, любой Windows-разработчик видит 29–43 «неотформатированных» файла и
  привыкает игнорировать вывод инструмента.
- **`git archive` + `tar` на Windows сам добавляет CRLF**: первая проверка канона
  через archive выдала 43 «битых» файла вместо одного. Не используйте archive
  для проверок формата на этой машине.
- **Одиночный CR внутри файла workflow ломает YAML**: YAML считает CR переводом
  строки, поэтому комментарий «съезжает» и следующая часть строки становится
  ключом маппинга (`can not read a block mapping entry; a multiline key may not
  be an implicit key`). Случалось реально: backslash в тексте heredoc превращался
  в `\r`, и файл переставал парситься. Валидатор (§11) теперь ищет `String.fromCharCode(13)`
  в файле, а не только парные CRLF.
- **`psql` без `PGCONNECT_TIMEOUT` может ждать пароль вечно** — интерактивный
  промпт в неинтерактивной оболочке выглядит как зависшая команда. Все вызовы
  оборачивайте в `timeout`.

---

- **Предупреждение git при коммите** «warning: in the working copy of ...
  LF will be replaced by CRLF the next time Git touches it» — это `core.autocrlf`
  на конкретной машине, а не ошибка файла: в индексе остаётся LF, и раннер читает
  workflow нормально (прогон `42088228822` зелёный). Лечится тем же
  `.gitattributes`, если команда решит его завести; бороться с предупреждением
  в каждом коммите не нужно.

## 7. Секретов в CI нет — и это проверяется

- Ни один step не использует `secrets.*` (валидатор проверяет и печатает
  «использовано secrets: ни одного»).
- `.env` в пайплайне не подключается и не создаётся.
- Тесты Go и web не требуют живого стенда: им хватает сервисного контейнера и
  фикстур.
- **Пароль тестовой БД удалён из файла.** Первая редакция держала
  `talentro-ci` — формально не секрет (одноразовая база), но он плодит привычку
  писать литералы в workflow, а при копировании файла в другой job такой
  «псевдо-пароль» уже выглядит настоящим. Теперь `POSTGRES_HOST_AUTH_METHOD:
  trust` и DSN без пароля. `trust` здесь допустим ровно потому, что порт
  опубликован только на loopback одноразовой VM раннера, база умирает вместе с
  job'ом и данных там нет, кроме сидов.
- Если однажды понадобится настоящий секрет (токен Vercel, SSH на VDS) —
  `environment` secrets GitHub и маскирование в логе, а не строка в YAML.

## 8. Приёмка против собранного стенда: как надо и почему это НЕ workflow

`docs/acceptance/recheck-stand.mjs` — ускоренная повторная приёмка витрины по
матрице `docs/acceptance/stand-gaps-2026-11-04.md` (HTTP-коды маршрутов и
фильтров, страницы организаций, карта, сессия тестировщика, чипы категорий,
`/media/**`, плюс прогон `check-category-icons.mjs`). Скрипт только читает
(POST `/api/auth/login` и `/register` не дёргает), exit code 1 — если есть
FAIL.

Как его прогонять правильно — вручную, против собранного docker-compose-стенда:

```bash
# 1. Поднять стенд вместе с БД, сидами и медиа
docker compose up -d --build

# 2. Дождаться готовности (api тянет схему из init.sql при первом старте)
docker compose ps
curl -fsS http://127.0.0.1:8080/healthz

# 3. Прогнать приёмку против этого стенда
node docs/acceptance/recheck-stand.mjs \
  --web=http://127.0.0.1:3000 --api=http://127.0.0.1:8080

#или через env, плюс кука тестировщика и путь к чужому скрипту иконок:
WEB_URL=http://127.0.0.1:3000 API_URL=http://127.0.0.1:8080 \
TESTER_TOKEN=... ICON_CHECK_SCRIPT=docs/acceptance/check-category-icons.mjs \
RECHECK_TIMEOUT_MS=15000 node docs/acceptance/recheck-stand.mjs
```

Почему этого **сознательно нет** в `ci.yml`:

1. нужен Docker-демон и собранная связка `db + api + web + caddy`, а это
   десятки минут и гигабайты на каждый пуш;
2. нужен `TESTER_TOKEN` — то есть секрет, против которого §7;
3. приёмка проверяет **состояние стенда** (данные, медиа, конфигурация), а не
   регрессию в коде: сеть, чужой деплой или пустая база давали бы красные
   job'ы, не связанные с диффом, — ровно то, из-за чего гейт перестают читать;
4. в этой задаче не было ни доступа к стенду из моего дерева, ни права его
   перезапускать (порты 3000/8080/55432 заняты чужими сервисами), поэтому
   прогон `recheck-stand.mjs` я **не выполнял** и не утверждаю, что он зелёный.

Как сделать это в CI позже, когда решим: отдельный `workflow_dispatch`-workflow
(не на каждый пуш), `runs-on: ubuntu-latest`, шаги `docker compose up -d --build`
→ ждём healthcheck → `node docs/acceptance/recheck-stand.mjs` → `docker compose
logs` в артефакт → `docker compose down`. И только после того как `main` будет
устойчиво зелёным под текущим гейтом.

## 9. Что CI не покрывает

- `golangci-lint` (Makefile использует его, если он установлен; в CI только
  `go vet`), тесты с `-race`, покрытие;
- сборка Docker-образов и валидация `docker-compose.yml`;
- e2e/Playwright и какие-либо прогоны против живого стенда (§8);
- линтинг SQL, миграции на боевой базе, `checks.sql` из `backend/Talentro/Makefile`;
- деплой (витрину на Vercel и VDS публикует человек — `docs/vercel.md`,
  `docs/deploy.md`);
- legacy-модуль `backend/go.mod`;
- кэш `.next` и артефакты сборки (job'ы ничего не складывают в артефакты).

## 11. Как проверить workflow без GitHub и без Docker-демона

1. **Разобрать YAML и проверить структуру** — самописный валидатор
   (`js-yaml` берётся из `web/node_modules`), вне репозитория, чтобы не засорять
   дерево. Проверяет: табы, BOM, одиночный CR, парсится ли файл, назван ли ключ
   триггера именно `'on'` строкой, список триггеров и `push.branches`,
   `timeout-minutes` у job'ов, разрешимость `needs`, что каждая `if:` ссылается
   на реально объявленный `needs.<job>.outputs.<name>`, образы `services`,
   существование каждого `working-directory` на диске, запиненные версии actions,
   пустые `${{ }}`, использование `secrets.*` и подключение `.env`.
2. **Проверить каждый `run`-блок** — вынуть их из YAML (`js-yaml` → файлы) и
   прогнать `bash -n`. Это ловит незакрытые кавычки и сломанные heredoc, но не
   семантику: `bash -n` не знает, что `grep` вернёт 1.
3. **Локально воспроизвести команды гейтов** (§10.2) — то, что не требует демона.
4. **Прогнать на GitHub** — `workflow_dispatch` или пуш в рабочую ветку. С
   публичного репозитория без токена читаются: список workflow'ов, прогоны,
   job'ы со **степ-конклюшенами**, аннотации (`/check-runs/{job_id}/annotations`).
   **Логи job'а (403) доступны только авторизованному** — именно поэтому шаги
   печатают диагноз аннотациями, а не только в лог.
