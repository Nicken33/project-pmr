# Подтверждение почты — инструкция для разработчика и ИИ фронтенда

## Что изменилось

Обычная регистрация теперь состоит из заполнения формы и подтверждения письма. До подтверждения в таблице `users` аккаунта нет. Поэтому до подтверждения невозможно войти, голосовать, писать отзывы и публиковать секции.

Существующие пользователи продолжают входить без дополнительного подтверждения. Вход через Google остаётся прежним — Google уже подтверждает email. Проверка писем регистрации и восстановление пароля используют разные таблицы и ссылки; их токены невзаимозаменяемы.

Эта задача меняет только базу и Go-бэкенд. Фронтенд ещё должен подключить описанный ниже сценарий. Его файлы при реализации этой задачи не изменялись.

## Адрес API и формат запросов

Все перечисленные маршруты находятся на домене Go-бэкенда. `BASE` — его адрес без `/api` в конце, например `https://vma8759072.s-vps.cloud`. Для локальной разработки — `http://localhost:8080`.

Метод для всех трёх запросов — `POST`, заголовок `Content-Type: application/json`. Авторизация не нужна. Не передавать Bearer-токен Google или существующую сессию вместо токена из письма.

Если сайт обращается к API через собственный прокси, добавить туда эти маршруты и передавать ответ Go без изменения HTTP-статуса. Если сайт обращается напрямую, в CORS Go должен быть разрешён домен сайта.

## 1. Начало регистрации

`POST /api/v1/auth/register`

```json
{
  "email": "my-address@example.com",
  "password": "example-password123",
  "name": "Матвей",
  "account_type": "section_owner"
}
```

Поля:

| Поле | Значения |
|---|---|
| `email` | Корректный email; сервер убирает пробелы по краям и переводит в нижний регистр |
| `password` | От 8 до 256 байт UTF-8; пробелы в пароле сервер не убирает |
| `name` | Непустое имя, максимум 120 байт UTF-8 после удаления пробелов по краям |
| `account_type` | `user`, `section_owner`, `service_owner`; при пропуске — `user` |

Отправлять `account_type`, а не `role`. Другие поля строгий JSON-декодер отклоняет.

Успешный ответ — **202 Accepted**:

```json
{
  "needs_email_verification": true,
  "email": "my-address@example.com",
  "message": "Открой письмо и подтверди почту, затем войди с паролем"
}
```

**В ответе нет `token` и `user`. Это ещё не вход.** Не записывать пустую сессию, не показывать «Вы вошли», не переходить в кабинет и не запрашивать `/api/v1/me` как обязательное продолжение регистрации. Показать экран «Проверь почту» с адресом, пояснением про папку «Спам» и кнопкой повторной отправки.

Если форма регистрации отправлена заново после минутной паузы, её данные заменяют предыдущую незавершённую заявку, а старая ссылка становится недействительной. Email уже созданного аккаунта даёт `409 email_taken`; пароль и роль существующего пользователя не изменяются.

Лимит — 3 попытки регистрации в час на IP. Для одной незавершённой регистрации — минимум 60 секунд между письмами.

## 2. Страница по ссылке из письма

Сервер отправляет ссылку вида:

```text
https://ДОМЕН-ФРОНТЕНДА/verify-email?token=ОДНОРАЗОВЫЙ_ТОКЕН
```

Домен берётся из серверной переменной `FRONTEND_URL`. Это ссылка на страницу фронтенда, а не на Go API. Фронтенду нужно реализовать `/verify-email`, включая открытие по прямой ссылке и обновление страницы. Для SPA на Vercel нужен соответствующий fallback на приложение; для Next — реальная страница этого маршрута.

На странице:

1. Прочитать `token` из query string. Никаких `code`, `id` или `credential` вместо него.
2. Показать кнопку «Подтвердить почту». Не делать подтверждение обычным GET: предпросмотр письма или сканер ссылок не должен создавать аккаунт.
3. По нажатию отправить `POST /api/v1/auth/email-verification/confirm` с JSON ниже. Заблокировать кнопку на время запроса, не отправлять параллельные дубликаты.
4. При успехе показать «Почта подтверждена, теперь войдите» и ссылку на обычный вход. Сервер намеренно не выдаёт сессию при подтверждении.
5. Убрать токен из адресной строки после завершения обработки. Не сохранять его в localStorage, метрики или логи. На этой странице желательно поставить `Referrer-Policy: no-referrer`.

```json
{"token":"ОДНОРАЗОВЫЙ_ТОКЕН_ИЗ_ПИСЬМА"}
```

Успешный ответ — **200 OK**:

```json
{"message":"Почта подтверждена, аккаунт создан. Теперь можно войти"}
```

Ссылка действует 15 минут. Повторное использование, истёкшая ссылка или ссылка, заменённая повторным письмом, дают `400 invalid_token`. Показать понятное сообщение и предложить запросить новое письмо или перейти ко входу, если подтверждение уже прошло. Не повторять POST автоматически после обновления страницы.

Если пользователь уже создал аккаунт через Google, пока письмо ожидало подтверждения, сервер вернёт `409 email_taken` с предложением войти. Его пароль, имя и роль этим письмом не перезаписываются.

Лимит — 10 попыток подтверждения в минуту на IP.

## 3. Повторная отправка

`POST /api/v1/auth/email-verification/resend`

```json
{"email":"my-address@example.com"}
```

Успешный ответ — **200 OK**:

```json
{"message":"Если регистрация ожидает подтверждения, письмо будет отправлено. Проверь почту и папку спам"}
```

Этот ответ одинаков для незнакомого адреса, уже зарегистрированного пользователя, недавно отправленного письма и заявки старше 24 часов. Он не гарантирует отправку нового письма в каждом случае. Новый токен выдаётся только для незавершённой регистрации, созданной менее 24 часов назад, с паузой минимум 60 секунд между письмами. После 24 часов нужно снова заполнить форму регистрации.

В интерфейсе после успешного запроса запускай таймер 60 секунд. Новая ссылка действует 15 минут, а предыдущая перестаёт работать. Лимиты повторной отправки — 10 запросов в час на IP и 3 запроса в час на адрес; лимит адреса возвращает тот же общий ответ 200. Лимитер в Go хранится в памяти процесса, а пауза 60 секунд дополнительно проверяется в PostgreSQL.

## 4. Вход, Google и профиль

Обычный вход остаётся `POST /api/v1/auth/login` с `{email,password}`. После подтверждения возвращает прежний `200 {token,user}`. До подтверждения аккаунта нет, поэтому вход возвращает `401 invalid_credentials`. Не проверяй наличие аккаунта по этому ответу; предлагай подтверждение после регистрации и повторную отправку письма отдельной кнопкой.

`POST /api/auth/google` остаётся без изменений: Google OAuth access token в `credential`, существующий аккаунт — `200 {token,user}`, новому пользователю — `202 needs_account_type:true`, затем повтор с `account_type`. Не путать два разных ответа 202:

| Признак | Что рисует фронтенд |
|---|---|
| `needs_email_verification:true` | Проверь почту |
| `needs_account_type:true` | Выбери тип аккаунта для Google |

В `PUT /api/v1/me` теперь можно изменить имя, передав текущий email и новое имя. Смена email пока запрещена с `400 email_change_requires_verification`, чтобы подтверждение нельзя было обойти через профиль. Отдельного сценария подтверждения новой почты пока нет. На фронтенде сделать email в профиле доступным для просмотра, а имя — для редактирования.

## 5. Ошибки

Формат:

```json
{"error":{"code":"invalid_token","message":"ссылка подтверждения недействительна или истекла"}}
```

| HTTP / code | Действие интерфейса |
|---|---|
| `400 invalid_body` | Исправить JSON и имена полей |
| `400 invalid_fields` | Показать сообщение проверки регистрации |
| `400 invalid_email` | Исправить адрес при повторной отправке |
| `400 invalid_token` | Показать, что ссылка истекла/уже использована, предложить новое письмо или вход |
| `409 email_taken` | Предложить вход или восстановление пароля |
| `429 rate_limited` | Прекратить повторные запросы; при наличии учитывать `Retry-After` |
| `503 email_unavailable` | SMTP не настроен; сообщить администратору |
| `503 email_delivery_failed` | Письмо отправить не удалось; заявка сохранена, через минуту можно повторить отправку |
| `500 internal_error` | Показать ошибку сервера; проверить миграцию и логи |

У первоначальной регистрации в минутном cooldown есть заголовок `Retry-After: 60`; у остальных ограничений заголовок может отсутствовать. Не пытайся лечить ошибку регистрации вызовом login или созданием локальной сессии.

## 6. Что нужно на сервере

Перед запуском обновлённого API применить `database/migrations/009_email_registration_confirmation.sql`. Если файлов 007/008 нет, это не мешает этой миграции — она от них не зависит. Не применять старые миграции заново без необходимости.

Используются те же настройки, что для восстановления пароля:

```ini
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=служебная-почта
SMTP_PASSWORD=пароль-приложения
SMTP_FROM=служебная-почта
FRONTEND_URL=https://реальный-домен-сайта
```

Новых почтовых сервисов и новых Google Client ID не требуется. `FRONTEND_URL` — адрес сайта без `/verify-email` и без `/api`. Не публиковать значения SMTP_PASSWORD и JWT_SECRET в репозитории или документации фронтенда.

После доставки файла на VPS выполнить в обычном терминале сервера, а не в psql:

```bash
docker exec -i talentro-db-1 psql -v ON_ERROR_STOP=1 -U talentro -d talentro < /opt/talentro/database/migrations/009_email_registration_confirmation.sql
```

Затем выложить обновлённый API и фронтенд с новым сценарием регистрации. Пока фронтенд не поддерживает `needs_email_verification` и `/verify-email`, не включать это обновление API на рабочем сайте отдельно от него. Текущий фронтенд может ошибочно считать ответ 202 входом или показывать ошибку.

Миграция создаёт `pending_registrations`, не изменяет старые аккаунты. Подтверждение атомарно создаёт пользователя и удаляет заявку. В базе лежат только Argon2id-хеш пароля и SHA-256-хеш случайного 32-байтного токена. Сырые пароли и токены не сохраняются. Истёкшие заявки не дают доступа; для очистки ненужных данных можно периодически выполнять `DELETE FROM pending_registrations WHERE created_at < now() - interval '24 hours';`.

## 7. Минимальная проверка после подключения

Используй только почту, к которой у тебя есть доступ.

```bash
BASE="https://vma8759072.s-vps.cloud"
```

```bash
curl -i -X POST "$BASE/api/v1/auth/register" -H 'Content-Type: application/json' -d '{"email":"YOUR_EMAIL","password":"example-password123","name":"Проверка","account_type":"section_owner"}'
```

Ожидается 202 и письмо. Пока не подтверждали — login должен вернуть 401.

```bash
curl -i -X POST "$BASE/api/v1/auth/email-verification/confirm" -H 'Content-Type: application/json' -d '{"token":"TOKEN_FROM_EMAIL"}'
```

Ожидается 200. Повтор с тем же токеном — 400. После подтверждения:

```bash
curl -i -X POST "$BASE/api/v1/auth/login" -H 'Content-Type: application/json' -d '{"email":"YOUR_EMAIL","password":"example-password123"}'
```

Ожидается 200 с токеном и выбранным `account_type`. Для проверки повторной отправки создай отдельную незавершённую регистрацию, подожди минимум минуту, затем вызови:

```bash
curl -i -X POST "$BASE/api/v1/auth/email-verification/resend" -H 'Content-Type: application/json' -d '{"email":"YOUR_EMAIL"}'
```

Проверь, что новая ссылка работает, а старая — нет; что Google не требует письма; что старые пользователи продолжают входить; что после обновления страницы подтверждённая сессия не выдумывается локально.
