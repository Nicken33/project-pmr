# Сессия: кука `talentro_session`

Документ описывает ровно то, что реализовано в `internal/auth/session.go` и в
обработчиках `internal/delivery/http/handlers/auth*.go`. Это не план развития:
пункт «чего сознательно нет» — часть контракта, а не недоработка.

ТЗ (§12.1) требует «механизм сессий с использованием cookies» и запрещает
хранить состояние входа на клиенте. Реализация — подписанная HttpOnly-кука с
HMAC-SHA256: сервер ничего не запоминает о сессии, но отличает поддельную куку
от настоящей.

## Кука

| Атрибут | Значение | Откуда |
| --- | --- | --- |
| `Name` | `talentro_session` | `auth.CookieName` |
| `Path` | `/` | `Store.Set` |
| `HttpOnly` | всегда | JS не читает токен, XSS не уносит сессию |
| `SameSite` | `Lax` | POST-запросы чужого сайта куку не несут |
| `Secure` | см. ниже | `SecureRequest(r)` |
| `Max-Age` | `2592000` (30 суток) | `ttl` в `Store.Set` |

`Domain` не ставится: кука достаётся только тому хосту, который её выдал, —
поддомены сами решают, нужен ли им вход.

## Формат токена

```
base64url(JSON claims) + "." + base64url(HMAC-SHA256(base64url(JSON claims), SESSION_SECRET))
```

`base64url` — `RawURLEncoding` (без `=` на конце), поэтому в значении куки нет
символов, требующих экранирования. Сегменты ровно два, разделитель — первая
точка (`strings.Cut`); лишняя точка внутри payload невозможна, потому что
payload — base64url, а алфавит точки не содержит.

Сверяется подпись, а не «содержимое похоже»: `Decode` считает HMAC от
полученного первого сегмента и сравнивает его со вторым **в той кодировке, в
которой подпись пришла** (`hmac.Equal` по строкам). Декодировать присланную
подпись перед сравнением нельзя: `RawURLEncoding` отбрасывает неканонические
хвостовые биты, и подмена последнего символа иногда даёт ровно те же байты.

Никакого `alg`/`kid` в токене нет и быть не должно: алгоритм один, он зашит в
код. JWT-совместимости здесь нет сознательно — куку читает только этот сервис.

## Claims

| Поле в JSON | Тип | Смысл | Откуда берётся |
| --- | --- | --- | --- |
| `uid` | int64 | id строки `users.id` | база при входе; у тест-режима `0` |
| `email` | string, `omitempty` | письмо учётки | база |
| `name` | string, `omitempty` | имя для витрины | база / профиль Google |
| `picture` | string, `omitempty` | аватар | `users.avatar_url` / профиль Google |
| `role` | string | `users.account_type`: `user`, `owner_activity`, `owner_service`, `moderator`; у тестового входа — `tester` | база при входе; `tester` приходит только из куки, в словаре базы (§8 табл. 8) его нет |
| `provider` | string | `local` (почта и пароль), `google`, `token` (вход для проверки) | способ входа: `local` и `google` читаются из `users.provider`, `token` живёт только в куке |
| `tester` | bool | включать ли тестовые разделы витрины | `role == "tester"` |
| `exp` | int64 | unix-время конца жизни | проставляет `Set`, не вызывающий код |

`Exp <= now` — ошибка и на encode, и на decode: токена без срока не бывает,
иначе кука читалась бы ровно до момента выдачи.

## Выдача и отзыв

Выдают куку четыре входа: `POST /api/auth/login`, `POST /api/auth/register`
(регистрация сразу логинит, ответ `201`), `POST /api/auth/google`,
`POST /api/auth/tester`. Все они идут через `issueWith` → `Store.Set`.

`POST /api/auth/logout` зовёт `Store.Clear`. В коде это `MaxAge: -1` плюс
`Expires: time.Unix(0, 0).UTC()`, а на провод `net/http` превращает это в
`Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 UTC` — браузер удаляет куку сразу.
Значение пустое, атрибуты (`Path`, `HttpOnly`, `SameSite`, `Secure`) совпадают с
выданными, иначе браузер посчитал бы это новой кукой, а не удалением. Выход
анонима — `204`, а не ошибка: состояние уже нужное.

`GET /api/auth/me` — единственный способ узнать, кто вошёл. Нет куки или она
битая → `200` с телом `{"authenticated": false, "tester": false}`. Это не 401:
анонимный заход — обычное состояние витрины, а не ошибка запроса.

## Когда ставится `Secure`

`SecureRequest(r)` истинна в двух случаях:

1. `r.TLS != nil` — сервер сам видит TLS-соединение, это собственное
   наблюдение, доверять больше нечему.
2. `X-Forwarded-Proto: https` (регистр не важен) **и** пир — loopback или
   приватная сеть (`peerIsTrusted`).

Второе условие — не педантизм. Сам `api` на стенде слушает http, настоящий
протокол приходит только от прокси. Если бы заголовок читался у кого угодно,
посетитель ставил бы `X-Forwarded-Proto: https` на http-соединении, получал куку
с `Secure` и терял её же: браузер не шлёт `Secure`-куку по http, вход
«самостоятельно» разлогинивается.

Следствие для развёртывания: между браузером и `api` обязан стоять прокси
(Caddy) из приватной сети, либо `api` должен сам принимать TLS. Прямой доступ к
`api` по http из интернета даёт куку без `Secure`, и это честно отражает
протокол, а не маскирует его. Публичный reverse-proxy, который не перепишет
`X-Real-IP`, в свою очередь, сломает лимиты входа (см. `auth.ClientIP`).

## Роль: почему только из `GET /api/auth/me`

Клиент не объявляет свою роль серверу нигде: ни в заголовке, ни в теле, ни в
`localStorage`. Фронт показывает имя и разделы по ответу `GET /api/auth/me` —
это расшифрованная сервером кука, а не догадка браузера. Историческая «витрина в
тестовом режиме» включалась по подстроке почты в `localStorage` и потому
включалась у кого угодно; теперь признак `tester` живёт в подписанном токене.

Права на кабинет модерации (`/api/v1/moderation/**`) при этом берутся не из
куки, а из базы: обработчик по `uid` перечитывает `users.account_type` на каждый
запрос. Кука — это «кто ты», база — «что тебе можно». Удалённый или пониженный в
роли аккаунт теряет доступ немедленно, хотя его подписанная кука ещё не
просрочена.

## Чем пахнет смена `SESSION_SECRET`

Ключ входит в HMAC каждой куки. Новый ключ ≠ старый → `hmac.Equal` не сходится →
`Decode` отдаёт `ErrInvalid` → все прежние сессии перестают быть действующими,
всех разлогинивает. Отзывы по одному невозможны: для этого нужно серверное
хранилище сессий, которого нет (см. ниже).

Отсюда правила:

- `SESSION_SECRET` обязателен и не короче 32 байт (`config.Load`); короткий
  ключ перебирается офлайн, и «подписанная кука» становится открытой.
- Секрет не должен попадать в репозиторий и в логи.
- Плановая смена ключа = плановый разлогин всех. Ротации без разлога в этой
  схеме нет.
- Два процесса `api` обязаны иметь один и тот же секрет, иначе кука, выданная
  одним, вторым не признаётся.

## Чего сознательно нет

**Refresh-токенов.** Нет короткого access-токена, который надо продлевать:
один bearer — сама кука, срок 30 суток. Продление ничего не добавило бы к
безопасности, но добавило бы эндпоинт и второй класс «состояния входа».

**Ротации ключей.** Один активный секрет, без `kid` и без окна, в котором
принимаются оба ключа. Цена — см. предыдущий раздел: смена ключа разлогинивает
всех. Приёмлемо для MVP, где смена секрета — инцидент, а не рутинная операция.

**Серверного хранилища сессий.** Нет таблицы/Redis со списком живых сессий,
следовательно нет немедленного отзыва, «выйти на всех устройствах» и честной
статистики активных входов. Осознанный размен: состояние живёт на клиенте,
база не растёт на каждую сессию, а `api` остаётся stateless — можно запускать
копии без общей памяти. Отзыв ограничен сроком жизни куки; грубый отзыв —
смена `SESSION_SECRET`.

**Отдельного секрета кабинета.** `MODERATOR_TOKEN` конфигурация требовала с
появления модераторского среза (§9.12), но ни один обработчик её не читал, а без
значения `api` не стартовал. В этой ветке требование снято: доступ в кабинет
решают роль из куки и повторное чтение `users.account_type`
(`feat/moderation-api`, `handlers/moderation.go:290-328`). Переменная вернётся
только вместе с кодом, который её сверяет, — «секрет, который никто не проверяет»,
безопасности не добавляет, зато ломает запуск.

**CSRF-токена.** Заменяется тремя механизмами:

- `SameSite=Lax` — браузер не прикладывает куку к POST-запросу с чужого
  сайта. Все эндпоинты, которые что-то меняют (`register`, `login`, `google`,
  `tester`, `logout`), — POST, а `decodeJSON` отдельно проверяет метод: GET с
  подставным телом ничего не оформит. Кабинет модерации устроен так же: очередь
  читается GET-ом, решения принимаются POST-ом.
- Метод проверяется и в самом обработчике, а не только в роутере: `logout` по
  GET-ссылке с чужой страницы был бы возможен, потому что переходы-GET Lax
  отпускает.
- `SameSiteGuard` (`internal/delivery/http/same_site.go`) — второй, независимый
  от настроек куки рубеж: на `POST`/`PUT`/`PATCH`/`DELETE` отказывает, если
  браузер сам сказал, что запрос чужой. Отклоняются `Sec-Fetch-Site: cross-site`
  и `Origin`, чьё имя хоста не совпало с `Host` запроса и которого нет в
  `ALLOWED_ORIGINS`. `Origin: null` (изолированный iframe) и неразбираемый
  `Origin` — тоже отказ: принадлежность сайту снята намеренно, принимать её за
  свою нечем.

  Запрос без обоих заголовков проходит: их не присылают curl, приёмочная матрица
  и серверный прокси витрины, а приложить чужую куку такой клиент сам не может.
  Именно поэтому правило не ломает BFF: `route.ts` пересылает на api только
  `x-forwarded-proto` и `cookie`, без `Origin`.

  Сверка по имени хоста, а не по origin целиком: `http://localhost:3000` и
  `http://localhost:8080` — одно место в смысле SameSite, и стенд без обратного
  прокси (витрина на одном порту, api на другом) не должен выглядеть чужим.
  Схема и порт учитываются ровно в `ALLOWED_ORIGINS`, где их вписывает тот, кто
  знает топологию. Разные имена хостов (`localhost` против `127.0.0.1`) своими
  не считаются: для куки это разные места, и такой случай — за `ALLOWED_ORIGINS`.

Этого перестаёт хватать, когда появится:

1. любое состояниеизменяющее действие на GET (или на `<a>`/`<img>`, куда браузер
   пошлёт запрос-переход — Lax куку пропускает);
2. вход через `<iframe>`/вкладки с cross-site контекстом, где Lax-политика сама
   ломает работу — и тогда захочется `SameSite=None; Secure`, а с ним CSRF-токен
   становится обязательным, потому что None от Lax не защищает ничего;
3. публичный API с токеном в заголовке для сторонних клиентов;
4. второй независимый процесс, ставящий куку на тот же домен (поддомены,
   `Domain`-атрибут).

## Кабинет модерации поверх этой куки

Фронт строит кабинет (§3.8) на тех же сессиях, поэтому контракт такой (проверено
по `feat/moderation-api`, коммит `784e1cb`; маршруты кабинета влиты в `main`
коммитом `0dc446f` и есть в этой ветке — `internal/delivery/http/route.go:37-43`):

- **Кука та же** — `talentro_session`. Отдельного секрета кабинета нет:
  `MODERATOR_TOKEN` конфигурация больше не требует и ни один обработчик её не читал
  (см. «Чего сознательно нет» выше). Роль живёт в claims куки и на каждый запрос
  сверяется с `users.account_type` — отзыв роли отзывает доступ с живой кукой.
- **Заголовки ответа.** `Cache-Control: private` и `Vary: Cookie` ставятся до
  тела: 401 и 403 не должны оседать в общем кэше, а ответ зависит от куки.
- **Коды.**
  - `401` — куки нет или она не читается («нужна сессия модератора: войдите в
    кабинет»). Аноним не доходит до базы: `authorize` раньше `schemaReady`.
  - `403` — кука читается, но роль не модератор (ни в claims, ни по повторному
    чтению `users.account_type`).
  - `409` — заявка уже решена; решение не переписывается и не отзывается.
  - `400` — отказ без причины, битое тело, неизвестный `{id}` в пути.
  - `503` — две разные причины: не задан `SESSION_SECRET` (кабинет выключен) или
    в базе нет таблиц модерации («прогоните `database/init.sql`»). Витрина не
    должна показывать за этим 503 пустую очередь: пустой список на сломанной базе
    выглядит как правда, а она это 503.

**`Origin` не обязателен, но если прислан — сверяется.** Заголовка в обработчиках
кабинета нет, и «заголовок не прислан» сам по себе не 403: curl, матрица приёмки и
серверный BFF приходят без него. Сверку делает `SameSiteGuard` перед
обработчиком (`internal/delivery/http/same_site.go`, ставится в `cmd/app/main.go`
после `Logger` и `Recoverer`), и только на методы, которые что-то меняют: чужой
`Origin` или `Sec-Fetch-Site: cross-site` дают `403` с конвертом §9
(`{"error":{"code":403,"message":"запрос с чужого сайта"}}`), остальные ответы
эндпоинтов не меняются.

CORS-прослойка к этому не относится: она смотрит на `Origin` только у preflight
(`internal/delivery/http/cors.go:18-27`), а обычный POST от чужого origin пропускает
насквозь — блокирует чтение ответа браузер, которому не хватило
`Access-Control-Allow-Origin`, а не сервер. От самого сервера POST теперь закрывает
`SameSiteGuard` — про него абзацем выше. Для same-origin вызова с витрины заголовок
и не нужен.
Ссылка на «`moderation_test.go:197-202` требует Origin» относится к тесту пагинации
очереди (`internal/repository/moderation_test.go`), а не к HTTP.
