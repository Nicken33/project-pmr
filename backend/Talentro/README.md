# Talentro — backend

Серверная часть каталога детских секций и услуг. Принимает запросы от фронтенда, достаёт данные из PostgreSQL и отдаёт их в формате JSON.

Стек: Go, роутер [chi](https://github.com/go-chi/chi), PostgreSQL 18, драйвер [lib/pq](https://github.com/lib/pq). Клиент — Next.js из папки `web/`.

Контракт: человекочитаемый — `API.md` рядом с этим файлом, машиночитаемый — `docs/openapi.yaml` в корне репозитория (§6.1). Набор маршрутов в chi и набор операций в спецификации сверяются тестами (`internal/delivery/http/route_test.go`, `openapi_test.go`), поэтому расхождение ловится до релиза, а не на клиенте.

## Как это устроено

```
браузер → CORS → logger → Recoverer → handler → repository → PostgreSQL
браузер ← JSON ← модель ← строки таблиц
```

- **handler** (`internal/delivery/http/handlers`) принимает запрос, разбирает и проверяет параметры и отдаёт JSON.
- **repository** (`internal/repository`) собирает SQL-запрос и общается с базой.
- **models** (`internal/models`) — структуры, в которые складываются данные из базы и которые превращаются в JSON.
- **httpx** (`internal/httpx`) — единый конверт ошибок §9 и запись JSON с явным charset.
- **config** (`internal/config`) — настройки из `.env` и переменных окружения.

CORS стоит первым не случайно: preflight (`OPTIONS`) должен обслуживаться до лога и до 404.

Правило слоёв: handler знает про repository, repository знает про базу и models. Обратных зависимостей нет.

## Быстрый старт

### 1. База данных

Нужен PostgreSQL 18. Проще всего через Docker:

```bash
docker run -d --name pg \
  -e POSTGRES_PASSWORD=<админский_пароль> \
  -p 127.0.0.1:5432:5432 \
  -v pgdata:/var/lib/postgresql \
  postgres:18-alpine
```

Порт привязан к `127.0.0.1`, чтобы база не была доступна из сети.

Схема и демо-данные живут в `database/init.sql` (в корне репозитория, не в этой папке). Скрипт идемпотентен — можно гонять по кругу на чистой базе; на базе со СТАРОЙ формой `cards` он падает сразу и внятной строкой, а не тихо портя данные.

```bash
createdb -U postgres main_db
psql -U postgres -d main_db -v ON_ERROR_STOP=1 -f ../../database/init.sql
```

`init.sql` не создаёт роли и не выдаёт права — это делает администратор отдельным скриптом. Приложение работает под ролью `catalog_app` (чтение и запись данных), роль `postgres` для приложения не используется.

После загрузки схемы и после любых правок данных — проверки целостности:

```bash
make checks        # то же, что psql "$DATABASE_URL" -f ../../database/checks.sql
```

`database/checks.sql` — проверки §7.8. Ошибок быть не должно (тогда выход 0), предупреждения допустимы: они про полноту демо-данных, а не про запреты схемы.

### 2. Настройки

Настройки читаются из `.env` (рядом с `go.mod`) или из окружения. `.env` в git не коммитится, образец — `.env.example`.

| Переменная | Обязательная | По умолчанию | Назначение |
|---|---|---|---|
| `PORT` | нет | `8080` | порт HTTP-сервера |
| `DATABASE_URL` | **да** | — | строка подключения к Postgres |
| `ALLOWED_ORIGINS` | нет | пусто | адреса фронта через запятую; пусто — междоменным запросам отказано |
| `SESSION_SECRET` | **да** | — | HMAC-ключ куки `talentro_session`, минимум 32 байта (`openssl rand -hex 32`). Без ключа любой посетитель соберёт себе сессию сам, короткий ключ перебирается офлайн — поэтому старт без них запрещён. Смена ключа разлогинивает всех |
| `TESTER_TOKEN` | нет | пусто | токен `POST /api/auth/tester`. Пусто — проверочный вход отключён (503), а не открыт всем |
| `GOOGLE_CLIENT_ID` | нет | пусто | web-клиент OAuth; сервер сверяет `aud` присланного токена. Пусто — `POST /api/auth/google` отвечает 503 |

```bash
export DATABASE_URL='postgresql://catalog_app:<пароль>@127.0.0.1:5432/main_db?sslmode=disable'
export SESSION_SECRET="$(openssl rand -hex 32)"   # подпись куки входа; на проде не менять
```

`MODERATOR_TOKEN` из списка убрана: её требовала конфигурация модераторского среза
(§9.12), но ни один обработчик её не читает, а без значения сервер не стартовал.
Требование, которое ничего не защищает, мешает приёмке — когда кабинет §3.8/§9.12
будет написан, переменная вернётся вместе с проверкой в коде.

`127.0.0.1` вместо `localhost` — чтобы не упереться в IPv6. `sslmode=disable` допустим только пока база и сервер на одной машине.

### 3. Запуск

```bash
cd backend/Talentro
make run        # то же, что go run ./cmd/app
```

В логе должно появиться «подключение к базе данных установлено». Сервер слушает `http://localhost:8080`.

Остановка по Ctrl+C или `docker stop` корректная: сигнал ловится до запуска goroutine с сервером, незакрытые ответы досылаются в течение 10 секунд, соединение с базой закрывается.

### `GET /api/v1/activities`

Параметры необязательные, комбинируются через `&`. Пустое значение (`?city=`) означает «фильтра нет», а не «пустая строка в SQL» (§5.8) — иначе не работают кнопка «назад» и пересланная ссылка.

| Параметр | Тип | Правило |
|---|---|---|
| `q` | строка | подстрока в названии, описании, организации и направлении; регистр и `ё` не важны, опечатки — нет (§5.1) |
| `city` | id или slug | город по точке проведения (§5.4) |
| `city_name` | строка | город по названию |
| `district` | строка, через запятую | район; **только вместе с `city`** — одноимённый район встречается в нескольких городах (§5.4) |
| `category` / `direction` | id или slug | направление; родитель выбирает и все его дочерние (§5.5) |
| `age` | число 1–120 | возраст ребёнка; группы без границы считаются подходящими, но услуги этот фильтр не берут (§5.2) |
| `price_max` | число ≥ 0 | диапазон группы проверяется по нижней границе (§5.3) |
| `free` | 1/0, true/false, yes/no | бесплатно — это `price_from = 0`, а не пустое поле (§7.4) |
| `online` | как `free` | `true` → формат `online` или `both`, `false` → только `offline` (§5.7) |
| `verified` | как `free` | контакты подтверждены менее 90 дней назад (§11.3) |
| `kind` | `activity` / `service` | тип карточки |
| `day` | 1–7 | день недели, 1 — понедельник (§5.6) |
| `time` | `ЧЧ:ММ` | занятие идёт в этот момент: время внутри `time_from…time_to` строки расписания (§5.6) |
| `near` | `широта,долгота` | точка в границах Приднестровья (45.9–48.9 / 27.4–30.6) |
| `radius` | 100–50000 метров | работает только с `near`; без него `near` означает «у точки есть координаты» |
| `sort` | `updated` / `price` / `name` / `verified` | по умолчанию — свежие сверху; `rating` появится вместе с таблицей голосов |
| `page` | число от 1 | номер страницы (§9.4) |
| `limit` | 1–100, по умолчанию 20 | размер страницы (§9.4) |

Ответ:

```json
{ "items": [ { "…": "карточка" } ], "total": 8, "page": 1, "limit": 20 }
```

`total` — сколько карточек подходит под фильтр всего, а не только на этой странице. Одна карточка — ровно одна строка выдачи (§5.9): фильтры не размножают карточки, они выбирают, какая группа и какая точка поедут внутри неё. Пустая выдача — `items: []`, но справочники пустыми не бывают (§7.12).

Устаревший `GET /api/cards` отдаёт тот же массив без обёртки, а `total` — в заголовке `X-Total-Count`. Тип ответа не меняем, чтобы не ломать уже написанный клиент; путь удалён после перехода фронта на `/api/v1/activities`.

### `GET /api/v1/activities/{slug}`

Карточка целиком, плюс `organization`, `locations[]` (с фото и числом групп), `groups[]` (возраст, цена с периодом, места, `schedules[]`), `photos[]`, `videos[]`. Принимается и slug, и числовой id. Чужой slug или снятое с публикации занятие — 404.

### Кэш и ошибки

Публичные ответы идут с `Cache-Control: public, max-age=60` и слабым `ETag`; совпавший `If-None-Match` даёт 304 без тела (§9). Ошибки — один конверт (§9.3), `code` совпадает с HTTP-статусом, `fields` заполняется только на 400:

```json
{ "error": { "code": 400, "message": "проверь поля",
             "fields": { "district": "район передаётся только вместе с городом" } } }
```

Внутренности наружу не уходят: текст ошибки БД может содержать имена таблиц и фрагменты запроса, поэтому в ответе остаётся «серверная ошибка, попробуй позже», а в лог уходит целиком.

## Как строится запрос с фильтрами

Запрос собирается во время работы по тому, какие фильтры пришли:

1. Берётся основа: `SELECT DISTINCT ON (c.id) … FROM cards c JOIN groups g … JOIN locations l … WHERE c.status = 'published' AND c.is_active AND o.is_active AND l.is_active`.
2. Для каждого пришедшего фильтра дописывается условие `AND …` с номером заполнителя (`$1`, `$2`, …), а значение кладётся в срез `args`.
3. `DISTINCT ON (c.id)` схлопывает умножение строк от join'ов обратно в одну карточку; порядок внутри него решает, какая группа и какая точка покажутся внутри (ближайшая точка, если запрошен `near`, иначе самая дешёвая).
4. Тот же `where` второй раз уходит в `count(DISTINCT c.id)` — это `total`.
5. Запрос и значения отправляются базе раздельно: `db.Query(query, args...)`.

Значения от пользователя **никогда** не подставляются в текст SQL напрямую — только через `$N`. Исключение — служебные фрагменты (выражение расстояния, имя столбца сортировки), собранные из уже проверенных чисел и из белого списка.

## Правила при разработке

- Все `id` в базе — `bigint`, в Go это `int64`. Для JavaScript id отдаются строкой.
- Необязательные поля в базе (могут быть `NULL`) в структурах — указатели (`*string`, `*float64`).
- Количество и порядок колонок в `SELECT` должны совпадать с `Scan`.
- В публичную выдачу попадают только карточки `status = 'published'` и активные карточка, организация и точка. Удаления как такового нет — запись снимают с публикации флагом `is_active` (§7.18).
- Для сравнения без учёта регистра и `ё` в кириллице используется SQL-функция `fold()`, а не `lower()`: на этом кластере `lower()` до кириллицы не доходит. Индексы `gin (fold(name) gin_trgm_ops)` построены на том же выражении, поэтому `fold()` обязан стоять **с обеих сторон** сравнения, иначе LIKE не пойдёт через индекс.
- Спецсимволы LIKE (`%`, `_`, `\`) из пользовательского ввода экранируются: запрос «20_21» не должен превращаться в маску.
- Байты вне UTF-8 Postgres отвергает сам и отвечает ошибкой, поэтому строки из URL проверяются до запроса — иначе это 500 вместо честного 400 (§9.3).
- Если меняешь сид в `database/init.sql`, правь ожидаемые наборы в `internal/repository/catalog_test.go` и прогоняй `make checks`.
- Опечаток в именах папок и пакетов быть не должно: имя пакета совпадает с именем папки.

## Проверки

```bash
make fmt      # отформатировать код
make lint     # go vet (golangci-lint, если установлен, зови отдельно)
make test     # go test ./...
make checks   # database/checks.sh → checks.sql (§7.8): ошибки целостности = провал
```

`make checks` требует `psql` в `PATH` и строку подключения — в `DATABASE_URL` или в `.env` рядом с `go.mod`. На Windows mingw-`make` выполняет recipe через `cmd.exe`, поэтому shell-логика живёт в скрипте, а не в `Makefile`; из-за этого здесь же не работает только `make help` (он читает комментарии через `awk`) — список команд выше.

Часть тестов — интеграционные: они ходят в настоящий Postgres за подключением в `DATABASE_URL` и без поднятой базы пропускаются. Проверяют семантику фильтров §5 на сидах из `database/init.sql`.

## Безопасность

- Пароли и `.env` в git не коммитятся.
- База доступна только с локальной машины (`127.0.0.1`).
- Для рабочего окружения нужны новые пароли и включённое шифрование соединения с базой.
- `ALLOWED_ORIGINS` — белый список: чужой origin в preflight получает 403, а простой GET проходит без `Access-Control-Allow-Origin`, и браузер сам блокирует чтение ответа.

### Сессия: почему подписанная кука, а не JWT (§12.1)

§12.1 формулирует выбор так: «сессия — HTTP-only cookie с CSRF-флагом (или JWT на
24 ч, решить в PR и записать в README)». Выбрано первое, с оговоркой про
CSRF-флаг: вместо отдельного токена `SameSite=Lax` плюс проверка `Origin` против
`ALLOWED_ORIGINS` — ниже, почему этого хватает. Второй вариант (JWT на 24 часа)
пришёл бы с хранилищем отозванных подписей или с принудительным обновлением раз в
сутки; и то, и другое дороже того, что он даёт каталогу, где менять нечего, кроме
кабинета владельца (§3.8) — он ещё не написан.

`talentro_session` = claims в JSON, подписанные HMAC-SHA256 по `SESSION_SECRET`;
срок действия внутри подписи, поэтому подделать куку нельзя, а «просроченная» —
отклоняется на месте.

Что это стоит и почему устраивает:

- **не отзывчиво.** Выйти из всех устройств сразу нельзя — кука живёт 30 суток и
  хранится у браузера. Нужен отзыв — появится таблица сессий; пока этого в ТЗ нет.
- **не для машин.** Токен в заголовке (`Authorization`) был бы нужен мобильной
  оболочке и сторонним клиентам. Куку читает только браузер, и `SameSite=Lax`
  этому не мешает.
- **CSRF.** `SameSite=Lax` не отдаёт куку на POST со стороны чужого сайта, а все
  запросы, которые что-то меняют, — POST. Переход по ссылке (GET) куку несёт, но
  GET-эндпоинты каталога только читают. При публичном `api` на отдельном домене
  список `ALLOWED_ORIGINS` обязателен: без него preflight чужого origin получает
  403, а простой запрос проходит без `Access-Control-Allow-Origin`, и браузер сам
  не даёт прочитать ответ.

Пароль — argon2id, как требует тот же §12.1 (`m=65536, t=3, p=4`, ключ 32 байта,
соль 16), стоимость вписана в строку хэша, поэтому подорожание на новой машине не
ломает старые записи. Текст пароля, `password_hash`, `SESSION_SECRET` и токены в
ответы и в лог не попадают (§7.3, §12.1 — «в лог почта и токен не пишутся»);
неверная почта и неверный пароль дают один и тот же `401`, чтобы перебор не
читался ни по различию ответов, ни по времени (§3.7.1). Ограничения частоты
(§12.2) держит `internal/auth/limiter.go` — см. «Вход и регистрация» в `API.md`.
