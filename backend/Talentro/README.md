# Подключение фото и видео секций Talentro

## Цель

Подключить во фронтенде владельца секции загрузку, просмотр и удаление фотографий и видео.

Перед изменениями найди существующие API-клиент, механизм авторизации и форму редактирования секции. Используй их. Не меняй названия маршрутов и формат запросов без согласования с backend.

## Настройки и авторизация

Используй существующий адрес Go API из конфигурации фронтенда. В примерах ниже он называется `API_BASE_URL`, например:

```text
http://localhost:8080
```

Все запросы владельца требуют токен:

```http
Authorization: Bearer <token>
```

Используй существующий способ получения и хранения токена. Не добавляй второй механизм авторизации.

Фото и видео передаются как `multipart/form-data`. При отправке `FormData` не задавай заголовок `Content-Type` вручную: браузер сам задаёт его вместе с multipart boundary.

## Получение секции и списка медиа

### Список секций владельца

```http
GET /api/v1/me/activities
Authorization: Bearer <token>
```

### Получение одной секции

```http
GET /api/v1/me/activities/{activityId}
Authorization: Bearer <token>
```

Ответ содержит поля секции и массивы `photos` и `videos`, если в них есть элементы. ID в JSON — строки.

Пример:

```json
{
    "id": "7",
    "name": "Секция бокса",
    "status": "draft",
    "photos": [
        {
            "id": "21",
            "path": "activities/7/ab12cd34.jpg",
            "alt_text": "Занятие",
            "position": 0,
            "is_cover": true
        }
    ],
    "videos": [
        {
            "id": "22",
            "path": "activities/7/cd34ef56.mp4",
            "position": 0
        }
    ]
}
```

Пустые массивы могут отсутствовать в JSON, поэтому обрабатывай отсутствие `photos` или `videos` как пустой список.

Отдельного маршрута для списка видео нет: список приходит в ответе секции.

## Загрузка фотографии

Маршрут:

```http
POST /api/v1/upload
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

Поля формы:

| Поле          | Обязательно | Значение               |
| ------------- | ----------: | ---------------------- |
| `activity_id` |          да | ID секции владельца    |
| `file`        |          да | файл JPG, PNG или WebP |
| `caption`     |         нет | подпись к фото         |
| `source_url`  |         нет | источник изображения   |
| `license`     |         нет | информация о лицензии  |

Пример:

```js
const form = new FormData();
form.append("activity_id", String(activityId));
form.append("file", file);

if (caption) form.append("caption", caption);

const response = await fetch(`${API_BASE_URL}/api/v1/upload`, {
    method: "POST",
    headers: {
        Authorization: `Bearer ${token}`,
    },
    body: form,
});
```

При успехе сервер возвращает `201 Created` и JSON с `id`, `path`, `alt_text`, `position`, `is_cover`. Ограничение размера файла — 10 МБ. Формат проверяется по сигнатуре файла, а не по имени.

## Загрузка видео

Маршрут:

```http
POST /api/v1/me/activities/{activityId}/videos
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

Поле формы:

| Поле   | Обязательно | Значение |
| ------ | ----------: | -------- |
| `file` |          да | файл MP4 |

Пример:

```js
const form = new FormData();
form.append("file", file);

const response = await fetch(
    `${API_BASE_URL}/api/v1/me/activities/${activityId}/videos`,
    {
        method: "POST",
        headers: {
            Authorization: `Bearer ${token}`,
        },
        body: form,
    },
);
```

При успехе сервер возвращает `201 Created` и объект видео:

```json
{
    "id": "22",
    "path": "activities/7/cd34ef56.mp4",
    "position": 0
}
```

Текущий предел — 50 МБ. Файл сохраняется в папку секции `activities/{activityId}/`.

**Ограничение текущего backend-кода:** сейчас проверяется MP4-сигнатура, но `ffprobe` ещё не подключён. Поэтому фронтенд не должен обещать, что сервер проверяет длительность до 30 секунд или кодеки H.264/AAC. До подключения этой проверки сервер может принять MP4 с неподходящей длительностью или кодеком.

## Показ фотографий и видео

`path` — относительный путь к файлу, а не сами байты изображения/видео. Файлы раздаются Go-сервером через `/media/`.

Создавай URL так:

```js
const src = `${API_BASE_URL}/media/${media.path}`;
```

Фото:

```jsx
<img src={`${API_BASE_URL}/media/${photo.path}`} alt={photo.alt_text ?? ""} />
```

Видео:

```jsx
<video
    controls
    preload="metadata"
    src={`${API_BASE_URL}/media/${video.path}`}
/>
```

Не загружай файл в JSON и не кодируй его в base64. Для отображения браузер отдельно запрашивает файл по URL.

Маршрут `/media/` сейчас использует стандартный Go `FileServer`. Прямой доступ к известному URL файла предусмотрен. Не полагайся на доступность или недоступность списка файлов в папках.

## Удаление фотографии или видео

Маршрут общий для обоих типов:

```http
DELETE /api/v1/me/activities/{activityId}/media/{mediaId}
Authorization: Bearer <token>
```

В `{mediaId}` передавай `photo.id` или `video.id`.

Пример:

```js
const response = await fetch(
    `${API_BASE_URL}/api/v1/me/activities/${activityId}/media/${mediaId}`,
    {
        method: "DELETE",
        headers: {
            Authorization: `Bearer ${token}`,
        },
    },
);
```

При успехе приходит `204 No Content`, без JSON-тела. После успеха удали элемент из локального списка или заново получи секцию:

```http
GET /api/v1/me/activities/{activityId}
```

Backend проверяет, что ID медиа относится к указанной секции и она принадлежит текущему владельцу. Если запись не найдена или принадлежит другому владельцу, возвращается `404`.

При изменении медиа опубликованная секция переводится на повторную модерацию.

**Ограничение удаления:** текущий метод удаления ищет медиа с `media.activity_id = activityId`. Фото, связанные только с местом через `location_id`, этим маршрутом могут не удалиться. Загрузка фото и видео через описанные выше маршруты привязывает их к секции. Не показывай действие удаления для медиа, которое frontend не получил как принадлежащее владельцу; поддержку удаления фото уровня места нужно отдельно согласовать с backend.

После удаления записи из БД сервер удаляет файл с диска. Если удаление файла не получится, сервер записывает ошибку в лог; API всё равно отвечает `204`, потому что запись уже удалена из БД.

## Обработка ошибок

Формат API-ошибки:

```json
{
    "error": {
        "code": "invalid_upload",
        "message": "описание ошибки"
    }
}
```

Возможные статусы:

| Статус | Значение                                                                                                      |
| -----: | ------------------------------------------------------------------------------------------------------------- |
|  `201` | файл загружен и привязан                                                                                      |
|  `204` | медиа удалено                                                                                                 |
|  `400` | неверные данные или ошибка разбора загрузки                                                                   |
|  `401` | токен отсутствует, неверен или истёк                                                                          |
|  `403` | недостаточно прав владельца                                                                                   |
|  `404` | секция или медиа не найдены у текущего владельца                                                              |
|  `413` | размер файла превышает лимит; при слишком большом multipart-запросе текущий backend также может вернуть `400` |
|  `415` | неподдерживаемый формат фотографии                                                                            |
|  `500` | внутренняя ошибка или ошибка работы с БД/хранилищем                                                           |

Показывай пользователю значение `error.message`, если оно пришло. На время загрузки показывай состояние загрузки и блокируй повторное нажатие. После успеха обновляй состояние секции.

## Что проверить перед завершением

1. Владелец открывает свою секцию и видит текущие `photos` и `videos`.
2. Загрузка фото отправляет `activity_id` и `file`, затем новое фото появляется в списке.
3. Загрузка видео отправляет файл в `file`, затем ролик появляется в списке и воспроизводится через `<video controls>`.
4. Удаление отправляет ID секции и ID медиа, после ответа `204` элемент исчезает.
5. Ошибки авторизации, неподходящий файл и превышение размера показываются понятным сообщением.
6. Адрес frontend включён в backend-переменную `ALLOWED_ORIGINS`, иначе браузер может блокировать запросы из-за CORS.

При интеграции проверь фактический ответ Go API на запущенных backend и БД: наличие маршрута в коде само по себе не подтверждает, что текущая база принимает `media_type = 'video'` или что все сценарии уже прошли проверку.
