# Talentro — контракт API

Актуальный контракт сервера каталога: маршруты, параметры, форма ответа, коды ошибок.
Источник истины по полям — код (`internal/models/`), этот файл описывает то, что
реально отдаёт сервер на ветке `feat/backend-activities-api`. Маршруты, параметры и
схемы дублированы в машиночитаемом виде в `../../docs/openapi.yaml` (§6.1) — для
генерации клиентов; набор путей в нём сверен с таблицей маршрутов тестом
`TestOpenAPICoversRoutes`, так что расходиться они могут только вместе с ошибкой
теста. Сюда идут пояснения, примеры и частота `null`, которых в YAML не бывает.

Базовый адрес dev-стенда: `http://localhost:8080` (канонический стенд на `:8081`).
Все ответы — `application/json; charset=utf-8`.

## Правила, которые действуют везде

- **Id.** В карточке `id`, `org_id` — строка для id карточки (`"10"`) и число для
  `org_id`, `location_id`, `group_id`, `category_id`. В справочниках (`cities`,
  `districts`, `categories`) id — число. Ссылаются на карточку и организацию могут
  и по slug, и по числу (см. ниже).
- **null отдаётся явно.** `omitempty` в моделях нет: поле присутствует всегда, просто
  с `null`. Никогда не опирайся на «поля нет в JSON». Исключения — два поля
  справочников, объявленных с `omitempty`: `children` у листового направления и
  `city_id` у города. Их в JSON нет вообще, и это не то же самое, что `null`.
- **Пустые списки — `[]`, не `null`.** `items`, `groups`, `locations`, `photos`,
  `videos`, `schedules`, `activities`. `children` — см. исключение выше.
- **Даты:** `updated_at` — RFC3339 с таймзоной (`2026-11-04T12:34:56+03:00`),
  `contacts_verified_at` — `ГГГГ-ММ-ДД` или `null`. У карточки, организации и
  точки своя дата сверки; поля с одинаковым именем не перетекают друг в друга.
- **Время занятий** — строка `ЧЧ:ММ` локального времени, без даты и таймзоны
  (`"15:00"`). Дни недели: `1` — понедельник … `7` — воскресенье.
- **Цена.** `price` / `price_from` — целое в рублях ПМР. **`0` = бесплатно,
  `null` = цена не указана** — это разные смыслы (§7.4). `price_to` — верх
  диапазона, `null` = диапазон одноместный. `price_period` — `session`, `month`
  или `course` (других значений CHECK в схеме не допускает); у бесплатных групп
  может быть `null`.
- **Возраст.** `age.min` / `age.max` (в деталях — `age_from` / `age_to`),
  `null` = граница не задана. У услуг возраста нет по смыслу (§5.2).
- **Неизвестные параметры запроса игнорируются.** Например `?org=5` не сужает
  выдачу — список занятий организации отдаёт
  `GET /api/v1/organizations/{slug}`.
- **Пустое значение = фильтр снят.** `?city=` трактуется как «город не выбран», а
  не как «пустить пустую строку в SQL» (§5.8). Это держит рабочими кнопку «назад» и
  пересланную ссылку.

## Enum-значения

Зафиксированы CHECK-ами в схеме, за их пределы сервер не выходит:

| Поле | Значения |
|---|---|
| `kind` (карточка) | `activity`, `service` |
| `format` | `online`, `offline`, `both` |
| `lesson_type` | `individual`, `group`, `both`, `null` (у услуг всегда `null`) |
| `status` | `draft`, `on_moderation`, `rejected`, `published` (в публичной выдаче только `published`) |
| `price_period` | `session`, `month`, `course`, `null` |
| `org_type` (`organization.type`) | `школа`, `студия`, `дом творчества`, `спортшкола`, `частный мастер` |
| `categories.kind` | `activity`, `service`, `both` |
| `media.kind` | `photo`, `video` |
| `schedules.weekday` | `1`…`7`, где 1 — понедельник |
| `account_type` (в схеме, в выдаче ещё нет) | `user`, `owner_activity`, `owner_service`, `moderator` |

| `GET` | `/api/cities` | **legacy**: тот же справочник, что v1 |

| `POST` | `/api/auth/register` | `{authenticated, tester, role, name, email, provider}` + кука |
| `POST` | `/api/auth/login` | то же тело + кука |

| `POST` | `/api/auth/tester` | то же тело + кука (по `TESTER_TOKEN`) |
| `GET` | `/api/auth/me` | `{authenticated, tester}` у анонима; поля вошедшего — с кукой |
| `POST` | `/api/auth/logout` | `204`, кука снята |

Legacy-пути — совместимость для клиента, который пишет на них с 2026-10. Они
обслуживаются **теми же обработчиками**, что и v1: поле не меняло ни имени, ни
типа, новые поля только добавились. Ломать их нечем, дубликата логики тоже нет.
Удалятся после миграции клиентов на `/api/v1`.

`{slug}` у карточки и организации принимает и slug, и числовое id:
`/api/v1/activities/tiraspol-studiya-palitra` и `/api/v1/activities/1` — один ответ.

## `GET /api/v1/activities`

### Параметры

| Параметр | Тип | Значение |
|---|---|---|
| `q` | строка | подстрока в названии, описании, организации и направлении. Регистр и `ё`/`е` не важны; опечатки не прощаются (§5.1) |
| `city` | id или slug | город по точке проведения (`tiraspol`, `1`) (§5.4) |
| `city_name` | строка | город по названию (`Тирасполь`) |
| `district` | строка, через запятую | район по имени или slug. **Только вместе с `city`** — иначе 400 (§5.4) |
| `category`, `direction` | id или slug | направление; родитель тянет все дочерние (§5.5). `direction` — прежнее имя, работает так же |
| `age` | целое 1–120 | возраст ребёнка. Группа без границы считается подходящей; услуги фильтр не берут (§5.2) |
| `price_max` | целое ≥ 0 | нижняя граница диапазона группы не больше этого числа (§5.3) |
| `free` | `1`/`0`/`true`/`false`/`yes`/`no` | `price_from = 0` (§7.4) |
| `online` | как `free` | `true` → формат `online` или `both`; `false` → строго `offline` (§5.7) |
| `verified` | как `free` | контакты подтверждены менее 90 дней назад (§11.3) |
| `kind` | `activity` / `service` | тип карточки |
| `day` | 1–7 | день недели занятия (§5.6) |
| `time` | `ЧЧ:ММ` | занятие идёт в этот момент (внутри `time_from…time_to`) (§5.6) |
| `near` | `широта,долгота` | точка в границах Приднестровья: `45.9–48.9` / `27.4–30.6` |
| `radius` | целое 100–50000 | метров от `near`. Без `near` — 400 |
| `sort` | `updated` / `price` / `name` / `verified` | по умолчанию — новые сверху. `rating` вернёт 400, пока нет таблицы голосов |
| `page` | целое ≥ 1 | страница (§9.4) |
| `limit` | целое 1–100, по умолчанию 20 | размер страницы (§9.4) |

Значения, которые не проходят проверку, дают **400 с именем поля** в
`error.fields` — см. «Ошибки».

### Форма ответа

```json
{
  "items": [
    {
      "id": "10",
      "slug": "tiraspol-veselye-noty",
      "name": "Детская музыкальная школа «Весёлые ноты»",
      "kind": "activity",
      "org_id": 10,
      "city": "Тирасполь",
      "age": { "min": 4, "max": 6 },
      "link": null,
      "description": "Фортепиано, скрипка и сольфеджио. Отчётные концерты дважды в год.",
      "district": "Центр",
      "price": 200,
      "category": "Музыка",
      "org_slug": "dmsh-veselye-noty",
      "org_name": "ДМШ «Весёлые ноты»",
      "org_type": "дом творчества",
      "phone": "+373 777 01234",
      "address": "ул. Еврейская, 42",
      "lat": 46.8407,
      "lng": 29.6344,
      "location_id": 12,
      "location_name": "Большой зал",
      "group_id": 15,
      "group_name": "4–6 лет",
      "price_to": null,
      "price_period": "month",
      "seats": 10,
      "category_id": 11,
      "category_slug": "music",
      "super_category": "Творчество и искусство",
      "super_category_slug": "creative-arts",
      "format": "offline",
      "lesson_type": "group",
      "status": "published",
      "verified": true,
      "contacts_verified_at": "2026-10-06",
      "photo": null,
      "groups_count": 2,
      "locations_count": 1,
      "updated_at": "2026-11-04T15:59:27.53583+02:00"
    }
  ],
  "total": 8,
  "page": 1,
  "limit": 20
}
```

`total` — сколько карточек подходит под фильтр **всего**, а не на этой странице.
Одна карточка — ровно одна строка выдачи (§5.9): фильтры не размножают карточки,
они выбирают, какая группа и какая точка показаны в плоских полях.

**Какая группа и точка попадают в плоские поля.** Без `near` — самая дешёвая
подходящая группа (`price_from`), при равенстве — с меньшим id. С `near` — группа
ближайшей точки, внутри неё — самая дешёвая. Поэтому плоский `price` — это минимум
`price_from` по группам **только когда `near` не запрошен**; с `near` это цена
ближайшей точки. Полные данные — в `groups[]` на странице карточки.

Поля `city`, `district`, `address`, `lat`, `lng`, `location_*` — выбранной точки;
`age`, `price`, `price_to`, `price_period`, `seats`, `group_*` — выбранной группы.

`verified` — `contacts_verified_at` **самой карточки** не старше 90 дней (§11.3); у
организации и точки своё `contacts_verified_at`, они на этот флаг не влияют.
Дата в ответе карточки — настоящая, а не выдуманный `updated_at`: признак
отвечает «свежее ли ещё», дата — «когда именно сверяли». `null` в
`contacts_verified_at` означает «контакты карточки не сверялись», при этом
`verified` тоже `false`; различить эти два случая по одному флагу нельзя,
поэтому они едут раздельно.
`photo` — первый фото-файл карточки или `null`.

### Примеры

```bash
curl 'http://localhost:8080/api/v1/activities?city=tiraspol&age=8&limit=5'
curl 'http://localhost:8080/api/v1/activities?q=%D1%84%D0%BE%D1%80%D1%82%D0%B5%D0%BF%D0%B8%D0%B0%D0%BD%D0%BE'
curl 'http://localhost:8080/api/v1/activities?day=2&time=17:30&sort=price'
curl 'http://localhost:8080/api/v1/activities?near=46.8407,29.6344&radius=3000'
```

Кириллицу в URL кодируй percent-encoding'ом (`q=фортепиано` →
`q=%D1%84%D0%BE%D1%80%D1%82%D0%B5%D0%BF%D0%B8%D0%B0%D0%BD%D0%BE`). Байты, которые не
являются UTF-8, сервер не отдаёт в базу, а отвечает 400 с именем поля.

## Карточка целиком: `GET /api/v1/activities/{slug}`

Те же плоские поля (см. выше) плюс полные объекты. Отдельных эндпоинтов на группу
и точку нет — раскрытие строится отсюда.

`contacts_verified_at` карточки и `contacts_verified_at` организации/точки — разные
колонки. В сиде у карточки 10 дата сверки стоит, а у её организации и точки —
`null`: дата в плоских полях приходит из `cards`, а не из JOIN.

```json
{
  "id": "10",
  "slug": "tiraspol-veselye-noty",
  "…": "плоские поля карточки",
  "organization": {
    "id": 10, "slug": "dmsh-veselye-noty", "name": "ДМШ «Весёлые ноты»",
    "type": "дом творчества",
    "description": "Фортепиано, скрипка, аккордеон; хоровое и сольное пение.",
    "phone": "+373 777 01234", "email": null, "site": null,
    "address": "ул. Еврейская, 42", "city": "Тирасполь",
    "contacts_verified_at": null
  },
  "locations": [
    {
      "id": 12, "name": "Большой зал", "city": "Тирасполь", "district": "Центр",
      "address": "ул. Еврейская, 42", "lat": 46.8407, "lng": 29.6344,
      "phone": null, "contacts_verified_at": null, "groups_count": 2,
      "photos": []
    }
  ],
  "groups": [
    {
      "id": 15, "name": "4–6 лет",
      "age_from": 4, "age_to": 6,
      "price_from": 200, "price_to": null, "price_period": "month",
      "location_id": 12, "seats": 10,
      "schedules": [
        { "weekday": 2, "time_from": "15:00", "time_to": "16:00", "note": null, "seats": 10 },
        { "weekday": 4, "time_from": "15:00", "time_to": "16:00", "note": null, "seats": 10 }
      ]
    }
  ],
  "photos": [],
  "videos": []
}
```

- `locations[]` — все активные точки карточки, упорядочены по id. `groups_count` —
  сколько групп этой карточки ведутся в этой точке.
- `groups[]` — все группы; у группы возраст, цена с периодом, места, `location_id`
  и `schedules[]` (по строке на день, §8 таблица 6). `seats` на уровне группы и
  строки расписания — разные значения: строка может быть `null`, если места
  считаны по группе.
- `photos[]` / `videos[]` — медиа карточки, по `order_num`. Объект медиа выглядит
  так (`source_url` и `author` — требования §14 к источнику и правообладателю):

  ```json
  { "path": "/media/locations/1/studiya-palitra.jpg", "caption": null,
    "source_url": null, "author": null, "order_num": 1 }
  ```

  `path` — относительный путь, который отдаёт Caddy из `infra/`; полный адрес
  собирай сам (`https://<домен>${path}`). Абсолютных URL в базе нет.
- `locations[].photos` — фото именно этой точки, та же структура объекта. Точка без
  фото отдаёт `[]`.
- В detail-ответе плоские `group_*`/`location_*` показывают первую группу и первую
  точку (не «самую дешёвую»): полные данные лежат в `groups[]` и `locations[]`.

## Карточка организации: `GET /api/v1/organizations/{slug}`

```json
{
  "organization": {
    "id": 1, "slug": "studiya-palitra", "name": "Студия «Палитра»",
    "type": "дом творчества", "description": "…", "phone": "+373 777 01101",
    "email": null, "site": null, "address": "ул. 25 Октября, 62",
    "city": "Тирасполь", "contacts_verified_at": null
  },
  "activities": [ { "…": "карточка каталога, те же поля, что в items" } ],
  "total": 1
}
```

`activities` — только опубликованные карточки этой организации (§7.5), по названию,
не больше 100 штук. `total` — сколько их всего.

## Справочники

`GET /api/v1/categories` — дерево ровно двумя уровнями, порядок по `order_num`:

```json
[
  {
    "id": 1, "slug": "creative-arts", "name": "Творчество и искусство",
    "kind": "both", "icon": "palette", "order_num": 1,
    "children": [
      { "id": 10, "slug": "drawing", "name": "Рисование", "kind": "both",
        "icon": "palette", "order_num": 1 }
    ]
  }
]
```

`kind` — `activity` / `service` / `both`: какие типы карточек в направлении
разрешены (§7.2). У дочерних направлений `children` отсутствует (не `null`).

`GET /api/v1/cities` — `[{"id":1,"slug":"tiraspol","name":"Тирасполь"}, …]`, восемь
городов по `order_num`.

`GET /api/v1/districts?city=tiraspol` — `[{"id":1,"slug":"centr","name":"Центр","city_id":1}, …]`.
Без `city` — **400** с `fields.city` (§5.4): одноимённый район бывает в нескольких
городах, угадывать не будем.

Справочники непустые по построению (§7.12) — пустой массив здесь означает, что база
не загружена.

## Вход и регистрация (§3.7)

Четыре способа войти и один общий ответ. Все успешные входы ставят одну и ту же
куку и отдают одно и то же тело — различать их по формату ответа нельзя.

Кука: `talentro_session=<claims>.<подпись>` — JSON claims, подписанные
HMAC-SHA256 по `SESSION_SECRET`; `Path=/; HttpOnly; SameSite=Lax;
Max-Age=2592000` (30 суток, §3.7), плюс `Secure`, когда запрос действительно
пришёл по https: либо `r.TLS` у самого `api`, либо `X-Forwarded-Proto: https` от
пира из loopback/приватной сети (Caddy). От посетителя этот заголовок не
принимается: иначе он получает `Secure`-куку на http-соединении и браузер
перестаёт её присылать, то есть вход разлогинивается сам собой. Формат токена,
claims и чего в схеме сознательно нет — `docs/session-spec.md`. Срок живёт внутри
подписанных claims, поэтому куку, выданную вчера, сегодня подделать не проще, чем
перебрать подпись. Куку
сервер читает только ради `role`, `tester` и имени вошедшего — прав на карточки
ещё не написано (§3.8, §9.12).

| Конечная точка | Тело запроса | Успех | Отказ |
|---|---|---|---|
| `POST /api/auth/register` | `{"email","password","name?"}` | `201` + кука | `400` поля, `403` чужой сайт, `409` занятая почта, `405`, `429`, `500` |
| `POST /api/auth/login` | `{"email","password"}` | `200` + кука | `400` битое тело, `401`, `403` чужой сайт, `405`, `429`, `500` |
| `POST /api/auth/google` | `{"credential"}` | `200` + кука | `400`, `401`, `403` чужой сайт, `405`, `409` (`fields.email`), `429`, `503` (не задан `GOOGLE_CLIENT_ID`) |
| `POST /api/auth/tester` | `{"token"}` | `200` + кука с `tester:true` | `400` битое тело, `401`, `403` чужой сайт, `405`, `429`, `503` (пустой `TESTER_TOKEN`) |
| `GET /api/auth/me` | — | `200` всегда: аноним = `{"authenticated":false,"tester":false}` | `405` |
| `POST /api/auth/logout` | — | `204`, кука снята (в коде `MaxAge:-1`, на проводе `Max-Age=0` и `Expires` в 1970) | `403` чужой сайт |

Ответ входа и `/me` (пустые поля не показываются, `omitempty`):

```json
{ "authenticated": true, "tester": false, "role": "user",
  "name": "Иван", "email": "ivan@example.com", "picture": null, "provider": "local" }
```

`role` — `account_type` из `users` (§7.8): `user`, `owner_activity`,
`owner_service`, `moderator`. `tester:true` бывает только после
`/api/auth/tester` и не берётся из тела ни на одном входе.

**Пароль.** Хранится как `$argon2id$v=19$m=65536,t=3,p=4$соль$хэш` — стоимость
лежит в самой строке, поэтому переназначение параметров на новой машине не
ломает старые хэши. Текст пароля, `password_hash`, `SESSION_SECRET` и
`TESTER_TOKEN` в ответы и в лог не попадают (§7.3, §12.1).

**Почта.** Нормализуется (trim + нижний регистр) до сверки и до вставки:
`users.email` уникальна (§3.7.1), а Postgres сравнивает её регистрозависимо не
автоматически, поэтому `Ivan@X.com` и `ivan@x.com` иначе стали бы двумя
аккаунтами. Подтверждение по письму не требуется (§3.7.1); восстановление пароля
письмом тоже не готово — по §3.7.3 его делает модератор вручную.

**Отказ не выдаёт существование почты.** Неверный пароль и адрес, которого нет в
базе, дают байт-в-байт один `401 {"error":{"code":401,"message":"неверная почта
или пароль"}}`; при неизвестной почте пароль всё равно сверяется с хэшем-заглушкой,
чтобы время ответа не отличалось. Аккаунт, заведённый входом через сервис и без
пароля, отвечает тем же `401`. Единственная намеренная утечка — `409` на
регистрации занятого адреса: без неё человек зацикливается на форме, которая
«почему-то не проходит», и подсказка в `fields.email` («войди вместо
регистрации») нужнее строгой тайны.

**Ограничения частоты (§12.2).** Счётчик фиксированного окна в памяти процесса,
ключ — адрес посетителя (`X-Real-IP` от Caddy; без приватного пира за окном —
`RemoteAddr`). Превышение — `429` с `Retry-After` в секундах.

| Что | Лимит |
|---|---|
| вход с одного адреса | 10 попыток в минуту |
| регистрация с одного адреса | 3 в час |

Окно входа одно на все способы войти: пароль, токен проверки и Google считают
попытки в одном счётчике, иначе `10 в минуту` превратилось бы в «10 на каждый
эндпоинт». Счётчики входа и регистрации независимы, поэтому заблокированный по
регистрациям адрес входит в существующий аккаунт. Ответы `400` (битая форма)
квоту не расходуют: опечатка в пароле не должна съедать попытки. `409` —
расходует.

Тело всех POST-эндпоинтов входа ограничено 64 Киб (`http.MaxBytesReader`), а
память счётчика — 65536 адресов: дальше старые окна вытесняются, чем считать
дальше без потолка. Это цена состояния в памяти процесса — на нескольких копиях
`api` счётчики независимы (см. `docs/deploy.md`).

**Чужой сайт не выдаст и не снимет куку.** `SameSite=Lax` — первый рубеж, но он
срабатывает только в браузере жертвы и зависит от одной настройки куки. Второй
рубеж — прослойка `SameSiteGuard` (`internal/delivery/http/same_site.go`),
стоящая на всём дереве маршрутов: на `POST`/`PUT`/`PATCH`/`DELETE` она смотрит
`Sec-Fetch-Site` и `Origin` и при явном признаке чужого сайта отвечает
`403 {"error":{"code":403,"message":"запрос с чужого сайта"}` до обработчика, не
дав ни Set-Cookie, ни изменения состояния. `Origin` сверяется по хосту (витрина на
другом порту того же хоста — не чужой сайт), точная схема и порт задаются через
`ALLOWED_ORIGINS`. Запрос без обоих заголовков проходит: их не присылают curl,
приёмочная матрица и серверный прокси витрины
(`web/src/app/api/auth/[...action]/route.ts` пересылает только `accept`,
`content-type`, `x-forwarded-proto` и `cookie`), а сам он приложить чужую куку не
может. GET и preflight прослойка не задевает.

**Секрет из шаблона не поднимет процесс.** `SESSION_SECRET` и `TESTER_TOKEN`,
начатые с `CHANGE_ME` (значения из `.env.example`), — не секрет: длина у них
достаточная, так что обычная проверка их пропускает, а подпись куки при этом
известна любому, кто открыл репозиторий. `config.Load()` отказывает отдельно и
называет переменную, поэтому `docker compose up` с неотредактированным `.env`
падает в первую секунду, а не работает открыто. Сгенерировать: `openssl rand -hex
32`.

Проверить живым curl: `bash docs/acceptance/auth-curl.sh http://127.0.0.1:8082`
(40 строк матрицы; прогон сам расходует бюджет «3 регистрации/час», повтор в том
же часе упрётся в `429`).

## Кабинет владельца (§3.8) и медиа

Вход — тот же, что у витрины: кука `talentro_session`, которую выдаёт
`POST /api/auth/login`. Отдельного входа владельца нет и `MODERATOR_TOKEN`-подобного
секрета тоже: право решает `users.account_type`, перечитанный из базы на **каждый**
запрос (§12.1). Понижение роли закрывает кабинет сразу, а не по истечении куки.

Две роли и только они: `owner_activity` управляет карточками вида `activity`,
`owner_service` — вида `service`. Вид приходит от роли, а не от клиента: `kind` в
теле разрешён только равным ему, несоответствие — `403`, а не `400` (это выход за
пределы своего кабинета, а не опечатка в поле). `tester` и `moderator` кабинет не
открывают.

Коды различимы намеренно, поэтому проверка стоит внутри каждого обработчика, а не
middleware на группе:

| Код | Когда |
|---|---|
| `401` | куки нет, подпись не прошла, срок истёк |
| `403` | роль не владельца; карточка или организация чужая; вид не совпал с ролью |
| `404` | карточки/организации/медиафайла нет; у владельца нет своей организации |
| `409` | переход статуса не разрешён; галерея карточки в `published` или `on_moderation`; занятое место в галерее |
| `503` | не задан `SESSION_SECRET` либо в базе нет таблиц модерации |

Все ответы кабинета идут с `Cache-Control: private, no-store` и `Vary: Cookie`.
ETag здесь нет намеренно — на `private, no-store` он не даёт ничего.

### Карточки

`POST /api/v1/me/activities` создаёт **всегда** `draft`: `owner_id` берётся из
сессии, адрес строит сервер, публикация — решение модератора (§3.9). Полей
`owner_id`, `status`, `is_active`, `slug`, `reject_reason` в модели входа нет, а
лишние ключи тела разбор игнорирует — подделать владельца или сразу опубликоваться
нельзя даже теоретически. Карточка создаётся только при своей организации.

Переходы: `submit` разрешён из `draft` и `rejected` и пишет строку в
`moderation_applications` — своей очереди у владельца нет, модератор видит заявку в
`/api/v1/moderation/queue`. `unpublish` разрешён только из `published` и ставит
`draft` + `is_active=false`; публичный каталог исключает анкету по обоим признакам,
поэтому снятие видно на витрине сразу. Правка (`PUT`) разрешена только в `draft` и
`rejected`: на `on_moderation` анкету смотрит модератор, на `published` её сначала
надо снять.

Ответ `submit` — `{card, application_id, submitted_at}`, ответ `unpublish` —
`{card}`. Это **не** плоская деталь: клиент, читающий `card.status` прямо из тела,
получит `undefined`.

Деталь кабинета (`GET /api/v1/me/activities/{id}`) повторяет форму публичной
карточки — `organization`, `locations[]`, `groups[]`, `photos[]`, `videos[]` — но
видна в любом статусе, тогда как публичный `GET /api/v1/activities/{slug}` отдаёт
только `published`. Элементы `photos[]`/`videos[]` в кабинете дополнительно несут
`id` строки `media`: без него удалить файл нельзя. Публичный контракт этот `id` не
получает и не меняется.

### Загрузка и удаление медиа

`POST …/photos` и `POST …/videos` — `multipart/form-data`, файл в поле `file`;
необязательные `caption`, `source_url`, `author` (§14 — источник и правообладатель).
Тип определяется **по содержимому**, а не по расширению и не по `Content-Type`:
фото — JPEG/PNG/WebP до 10 МиБ, видео — MP4 (бокс `ftyp`) до 50 МиБ. SVG
отвергается: это активное содержимое, а не картинка (`415`). Лимит — 30 загрузок в
минуту на владельца (`429`).

Имя файла случайное, создание `O_EXCL` — существующий файл не перезаписывается.
`path` в ответе всегда начинается с `/media/`, как у засеянных строк: без префикса
браузер отрендерил бы его как `/cards/…`, и картинка молча стала бы `404`. Ответ
`201` — `{id, card_id, kind, path, caption, source_url, author, order_num}`; пять
полей `Media` выходят теми же именами, что в публичной галерее, поэтому клиент
кладёт ответ без перевода. `kind` выбирает маршрут, а не форма.

**На `published` и `on_moderation` любая правка галереи — `409`.** На витрине новое
фото попало бы в каталог без проверки модератора; на проверке оно подменило бы то,
что модератор смотрит, — `DecideApplication` ставит `published`, не перечитывая
медиа. Текст отказа называет следующий шаг: `unpublish` для витрины, «дождитесь
решения» для проверки. Статус при этом не меняется и заявка не создаётся. Проверка
владения стоит раньше проверки статуса, поэтому чужая закрытая карточка отвечает
`403`, а не `409`.

`DELETE …/media/{mediaID}` снимает строку и файл. Порядок именно такой: удалённый
файл при живой строке оставил бы галерею с битой картинкой и без способа её
починить. Право проверяется до обращения к диску (строка принадлежит этой
карточке, карточка — вызывающему), путь проверяется на локальность. Ответ `200` —
`{deleted: true, id, card_id}`.

### Где лежат файлы

Каталог задаёт `MEDIA_DIR` (по умолчанию `./media`), читает
`internal/config/config.go`. Раздаёт его сам Go-сервис: `GET` и `HEAD /media/*`,
`X-Content-Type-Options: nosniff`, активное содержимое — как `attachment`,
листинга каталога нет, симлинки и каталоги не отдаются. `HEAD` зарегистрирован
отдельно, потому что проверки деплоя спрашивают `curl -I`, а chi на `Get` ответил
бы `405`.

На VDS файлы обычно раздаёт Caddy с того же каталога (`handle_path /media/*`), и
тогда маршрут Go — запасной. **Каталог обязан быть одним и тем же для того, кто
пишет, и того, кто раздаёт**, и обязан переживать пересборку контейнера: том, а не
слой контейнера. Иначе загруженное фото легально лежит на диске и отдаёт `404` с
витрины. Подробности — `../../docs/deploy.md` и `../../docs/vercel.md`.

### Как это читает витрина

Прямых вызовов `/api/v1/me/*` из браузера нет: Next-прокси
`web/src/app/api/me/[...action]/route.ts` пересылает куку посетителя и возвращает
ответ бэкенда, как у кабинета модерации. Клиент — `web/src/lib/owner-api.ts`.

### Заведение первого владельца — только через базу

Кабинет готов кодом, но **самостоятельно стать владельцем нельзя**, и это надо
знать до релиза, а не после. Замерено на каноническом `database/init.sql`:

- Регистрация всегда пишет `account_type='user'` — и почтовая
  (`repository/users.go:87-88`), и Google (`users.go:26-27`). Поля `account_type`
  в теле не читаются, поэтому повысить себя запросом невозможно.
- В сиде четыре владельца (id 2–5, `owner_activity`), но `password_hash` у них
  NULL: вход отвечает `401` так же, как на неверный пароль (`auth_local.go:79-82`).
  Комментарий сида «вход по §3.7 ещё не реализован» устарел — вход реализован,
  паролей у этих строк просто нет.
- `owner_id` встречается в `init.sql` только в DDL (строки 272 и 334) и ни в одном
  INSERT: **ни одна засеянная карточка и ни одна организация владельца не имеют**.
- `PUT /api/v1/me/organization` — только UPDATE: организации нет → `404`.
  Эндпоинта создания первой организации в контракте нет, поэтому цепочка
  «зарегистрировался → создал организацию → создал карточку» обрывается на первом
  шаге.

Порядок для сисадмина: человек регистрируется сам через витрину (получает настоящий
`password_hash`), затем оператор повышает его и заводит организацию. Реквизиты
`NOT NULL` сверены с DDL: у организации обязательны `slug` (UNIQUE), `name`, `type`
из закрытого CHECK-списка, `phone` и `publish_basis` (§11.8).

```sql
-- 1. Роль. owner_activity — занятия, owner_service — услуги; вид карточек
--    выводится из роли, поэтому выбрать надо сразу правильный.
UPDATE users SET account_type = 'owner_activity'
 WHERE email = 'owner@example.com';

-- 2. Организация владельца. Без неё POST /api/v1/me/activities отвечает 404.
INSERT INTO organizations (slug, name, type, phone, publish_basis, owner_id)
VALUES ('studiya-primer', 'Студия «Пример»', 'студия', '+373 000 00000',
        'договор с владельцем от 2026-11-08',
        (SELECT id FROM users WHERE email = 'owner@example.com'));

-- 3. Необязательно: передать владельцу уже засеянную карточку.
UPDATE cards SET owner_id = (SELECT id FROM users WHERE email = 'owner@example.com')
 WHERE id = 1;
```

После этого владелец входит обычным `POST /api/auth/login` и создаёт карточки уже
сам: `owner_id` подставится из сессии, `org_id` возьмётся из его организации,
статус будет `draft`. Менять `account_type` на живой базе осторожно: роль
перечитывается на каждый запрос, поэтому понижение закрывает кабинет немедленно,
а уже выпущенные куки остаются валидными как сессии — они просто теряют права.

## Ошибки

Один конверт для всех ошибок (§9.3):

```json
{ "error": { "code": 400, "message": "проверь поля",
             "fields": { "district": "район передаётся только вместе с городом" } } }
```

| Статус | Когда | Что в ответе |
|---|---|---|
| `400` | значение параметра не проходит проверку (§5) | `message: "проверь поля"`, `fields` — поле → подсказка на русском |
| `404` | карточка/организация не найдена или снята с публикации; чужой slug | `message: "занятие не найдено или снято с публикации"` / `"организация не найдена или снята с публикации"` |
| `403` | preflight `OPTIONS` с origin вне `ALLOWED_ORIGINS` | пустое тело, заголовка `Access-Control-Allow-Origin` нет |
| `403` | `POST`/`PUT`/`PATCH`/`DELETE` с явным признаком чужого сайта (`Sec-Fetch-Site: cross-site` или `Origin`, который не свой и не в `ALLOWED_ORIGINS`) | `message: "запрос с чужого сайта"` |
| `500` | внутренняя ошибка | `message: "серверная ошибка, попробуй позже"`; текст ошибки БД уходит только в лог |
| `503` | `/health`, когда база не отвечает | `{"status":"error","database":"disconnected",…}` |

Примеры 400:

```json
{ "error": { "code": 400, "message": "проверь поля", "fields": { "age": "age — целое число от 1 до 120, возраст ребёнка" } } }
{ "error": { "code": 400, "message": "проверь поля", "fields": { "radius": "radius работает только вместе с near" } } }
{ "error": { "code": 400, "message": "проверь поля", "fields": { "sort": "sort — updated, price, name или verified; rating ещё не считается" } } }
{ "error": { "code": 400, "message": "проверь поля", "fields": { "q": "значение должно быть корректной строкой в UTF-8" } } }
```

`fields` ключи совпадают с именами параметров; для параметров пути — `slug` или
`id` (то имя, которое стоит в вызванном пути).

## Кэш, ETag и междоменные запросы

- Все публичные GET: `Cache-Control: public, max-age=60` (§9).
- Список и карточка отдают слабый `ETag`; `If-None-Match` с совпавшим тегом → `304`
  без тела. Метка списка считается по составу и порядку карточек страницы плюс
  `total`, метка карточки — по её id и `updated_at`; правка в базе сдвигает обе.
  У страницы организации и справочников ETag пока нет — только
  `Cache-Control`.
- `Access-Control-Allow-Origin` ставится только для origin из `ALLOWED_ORIGINS`,
  вместе с `Vary: Origin` и `Access-Control-Allow-Credentials: true`.
  Preflight (`OPTIONS`) отвечает `204` с методами, заголовками и
  `Access-Control-Max-Age: 600`. Чужой origin на preflight получает `403`, а
  обычный запрос проходит без CORS-заголовков — браузер сам блокирует чтение
  ответа, поэтому `curl` увидит 200, а фронт — ошибку доступа.

## Что реально заполнено на демо-стенде

Сид `database/init.sql`: 8 опубликованных карточек (7 занятий + 1 услуга), 10
организаций, 12 точек, 16 групп, 25 строк расписания. Полезно, чтобы мобильный
экран не падал на `null` там, где его быть не должно, и не ждал данных там, где их
в сиде нет.

| Поле | Состояние на стенде |
|---|---|
| `lat`, `lng` | заполнены у всех 8 — карта работает |
| `name`, `slug`, `city`, `phone`, `format`, `status`, `kind`, `updated_at` | заполнены у всех |
| `link` (сайт организации) | `null` у всех 8 |
| `price_to` | `null` у всех 8 в списке (диапазон есть только у группы 16, она не попадает в «самую дешёвую») |
| `district` | `null` в 4 карточках — районы заведены не для всех точек |
| `seats` | `null` в 3 |
| `price_period` | `null` в 2 (обе бесплатные) |
| `photo` | `null` в 1 (`tiraspol-veselye-noty`) |
| `lesson_type`, `age.min/max`, `group_name`, `location_name` | `null` у услуги `tiraspol-repetitor-matematika` — у услуги возраста и названия группы нет по смыслу |

| `videos[]` | пусто у всех — видео в сиде нет |

## Чего в контракте ещё нет

Не ломайся на этих ожиданиях — это отложенное, а не потерянное:

- **Роли решают права.** Вход готов (§3.7, см. «Вход и регистрация»), кабинет
  модерации (§3.9) и кабинет владельца (§3.8) — тоже: маршруты `/api/v1/moderation/*`
  и `/api/v1/me/*` в таблице выше. Роль берётся из `users.account_type` и
  перечитывается из базы на каждый запрос, а не из куки и не из тела. Фронту брать
  роль из `GET /api/auth/me`, а не из подстроки почты в `localStorage` —
  мок-авторизацию в клиент не включай: единственный источник состояния —
  `/api/auth/me`. Публичные маршруты каталога ролью не ограничены: они и должны
  быть открыты, ограничение стоит на кабинете.
- **Голоса, избранное, отзывы, журнал изменений** — таблиц нет, поэтому нет и
  `sort=rating`. Ветка `codex` предлагала `favorites`/`vote`/`recommended` под
  другую схему («v2», которой в `database/` нет); переносить их нечем — сначала
  таблицы и миграция, потом эндпоинты.
- **Мессенджеры.** Таблица `messengers` в схеме есть, в выдачу ещё не поднята:
  наружу идут только `phone`, `email`, `site` организации.
- **Фильтр по организации** в каталоге не предусмотрен §5 — используй
  `/api/v1/organizations/{slug}`.
